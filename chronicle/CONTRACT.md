# Chronicle v1.9 contract (2026-10-30)

Authoritative schema: `models/chronicle.baboon` (`chronicle.api`, `1.9.0`), the sole self-contained API model. Only this version's Scala and TypeScript codecs are generated; no historical schemas or cross-version converters are retained. Generated Scala: `generated/scala/chronicle/api/`; TypeScript: `generated/typescript/chronicle/api/`, with runtime at `generated/typescript/BaboonRuntime.ts` and `BaboonSharedRuntime.ts`. Use `Type_JsonCodec.instance.encode/decode(BaboonCodecContext.Default, value)`; do not use plain `JSON.stringify` on generated ADTs. ADTs encode as one-key objects (e.g. `{"Whoami":{}}`); enums encode their named string (`Lexical`, `Pi`, `Read`). UUID strings. Optional fields encode null. Timestamp metadata is ISO8601 string or null. Spans use UTF-8 byte offsets, half-open.

## HTTP/auth
- `POST /api/login`: legacy generated `LoginRequest` -> `LoginResponse`; password authentication sets the same durable `chronicle_session` as the account API. HttpOnly, host-only, SameSite=Strict, Secure except explicitly configured HTTP development/trusted private-network deployments.
- `POST /api/logout`: cookie + exact Origin, deletes the server session and clears the cookie.
- `POST /api/session/refresh`: cookie ONLY + exact Origin, no URL parameters; revalidates an existing session and enabled user, returns generated `UserInfo`, and resets the same cookie. `X-Chronicle-Session-Ttl-Seconds` is retained as a compatibility header but reports **cookie persistence**, 34560000 seconds (400 days), not a server session timeout. `Cache-Control: no-store`. New sessions have no idle or absolute server deadline; `sessionTtlSeconds` is a legacy configuration input with no effect on session or cookie lifetime. Cookie refresh does not mutate session authority or extend a server deadline. Browser eviction/caps can still require sign-in. Migration promotes only legacy sessions still live when the migration acquires its lock; expired/deleted/revoked sessions are never recreated. Explicit historical expiry boundaries remain enforced. Disabling/removing a configured user or replacing its password hash invalidates existing sessions persistently, including after later re-enabling/restoring the old password. Cookie refresh does not advance the security epoch; credential/principal changes, explicit expiry imposition/reduction and expired-row revival do.
- `GET /api/versions`: generated `VersionInfo`, public.
- `GET /api/ws`: cookie ONLY and exact configured Origin; text JSON `ClientEnvelope` -> `ServerEnvelope`. First operation Hello(versions containing `1.9.0`); only that version is accepted for the socket's lifetime. Removed and future-only offers return `version-mismatch` without a compatibility fallback. Repeated Hello is a protocol error. VersionInfo reports current `1.9.0`, minimum `1.9.0`, supported `[1.9.0]`. No browser HTTP version header is required. Per-request cookie/session/live-user authorization. Ping/Pong nonce heartbeat; server Ping uses a fresh envelope requestId, answer Pong with SAME requestId and nonce. 20s heartbeat / 10s pong deadline. Client Ping -> Result.Pong. Hello/Ping/Pong are consumed independently of serialized application work; its per-socket queue is bounded32 and saturation returns unavailable. Queued operations reauthenticate at execution; captured ordinary replies revalidate the same browser credential and owner again when pulled for delivery. The sole self-revoking exception is an explicitly tagged, already-committed Logout receipt, not arbitrary mutation results. Authentication-store delivery failures close retryably with1013; revoked/reassigned authority closes4401. MCP run delivery additionally retains its security-epoch and resource authority checks. No mutation replay on reconnect. Committed Logout acknowledgement is best effort: an earlier protected reply, revocation tick or transport failure can close the socket before its receipt is pulled. After fresh login, `Receipt(requestId)` recovers the durable result; the bypass does not give Logout priority over already queued replies.
- `POST /api/ingest`: bearer ONLY, Ingest scope; generated `IngestRequest` -> `IngestReceipt`; errors JSON Failure and non-2xx.
- `POST /api/jobs/v1`: bearer ONLY, a token with the OperateJobs account scope; the generated envelopes of exactly four operations ("Job operations for tokens" below).
- `POST /mcp`: bearer ONLY, Read scope (Raw additionally for raw, which is deliberately not an MCP tool). Stateless Streamable HTTP; JSON responses. Supported MCP versions 2025-11-25, 2025-06-18, 2025-03-26. GET returns 405; notifications return 202. Origin if present must match configured origin. No URL credentials anywhere.
- Database unavailable (restart-robustness spec §5): a REST request — the MCP request's bearer phase and the account plane (`/api/account/v1`, the account HTTP v1 endpoints) included — that gets no database connection (the admission full or timed out, none by the acquisition deadline, a fenced role, the server closing) or whose connection fails (SQLSTATE 08xxx, 57P01-57P03) is answered 503 `unavailable` with `Retry-After: 5` (previously REST and the MCP bearer phase answered 500; the account plane already answered 503 `unavailable`, and its imperative-account routes already added `Retry-After: 5`, its other routes — e.g. `GET /api/account/v1`, logout, tokens — did not); a later request may succeed. An MCP tool call's failure stays a JSON-RPC result with tool error `unavailable` in HTTP 200; WebSocket operations answer `unavailable` as before.

## Account HTTP v1 (independent of Baboon domain version)

All routes are under `/api/account/v1`. JSON is strict UTF-8, at most16KiB/depth8; duplicate keys, unexpected fields and ambiguous cookie/Origin/Host/Authorization headers are rejected. No query strings. Host must match the configured Origin's authority; Origin, when present, must match exactly and is required for every POST. POST requires `Content-Type: application/json`. Logout/issue/revoke additionally require exactly one `X-Account-Actor` copied from the displayed account user; this public opaque owner binding is checked against the current cookie owner inside the effect transaction. Missing/duplicate/malformed bindings return invalid400; a valid binding for another owner returns conflict409. This prevents an account switched in another tab from receiving an action intended for the previously displayed user; it is not an authentication credential. Browser-session cookie only: bearer tokens, including configured tokens, cannot access settings or mutations. All responses have `Cache-Control: no-store`; errors are sanitized `{ "error": { "code": "unauthorized|forbidden|not-found|invalid|conflict|too-large|unavailable", "message": "..." } }` with appropriate non2xx status. Database failure is unavailable, never invalid credentials. Credential values never occur in errors or logs.

- `POST /login` body `{login,password}` -> `{user:{id,login,displayName,actor}}` plus persistent cookie.
- `GET` root -> `{user:{id,login,displayName,actor},tokens:[{id,name,source:"configured"|"issued",createdAt:string|null,revoked:boolean,scopes:string[]}],scopes:["Ingest","Read","Raw"]}`. With the optional request header `X-Account-Scopes: all` (at most one; any other value or a second one is 400 `invalid`) the offered list is `["Ingest","Read","Raw","OperateJobs"]` and a token with OperateJobs lists it after its typed scopes; without the header every account answer is unchanged and names typed scopes only. OperateJobs is an account-plane scope ("Job operations for tokens"), not a `chronicle.api` `Scope` value. Only the current owner's tokens are listed, active tokens first, at most100 metadata entries. No token/session secret or password hash is returned.
- `POST /tokens` body `{name,scopes:string[]}` -> `{token:<listed metadata>,secret:string}`. Scopes are Chronicle's case-sensitive `Ingest`, `Read`, `Raw`, and `OperateJobs` only with `X-Account-Scopes: all` (else 400 `invalid`); nonempty/distinct, at most 16, Raw and OperateJobs require Read. The token is scoped to the authenticated owner and counts toward the shared100-active-token limit including configured tokens.
- `POST /tokens/{id}/revoke` body `{}` -> `{ok:true}`. Ownership and current browser authority are checked transactionally after the same owner mutation lock used by WS mint/revoke. Unknown/other-owner IDs return not-found; configured tokens are immutable server-side and return forbidden.
- `POST /logout` body `{}` -> `{ok:true}`, removes only the independent browser session, not API tokens.

### Imperative accounts (self-signup, admin enrollment)

Exist only while the server configuration sets `accounts.enabled` (the master switch). With it off — the default — none of the routes below is registered (they answer the same 404 as any unknown path), `POST /login` and the legacy `POST /api/login` take exactly the path above, and accounts created earlier are **suspended, not revoked**: their `ch_users` row is disabled at startup, their browser sessions are deleted by the existing rule for disabled owners, their API tokens are refused by the disabled-owner gate but kept, and all of it works again once the switch returns (sign-in is required again). Turning `signup.enabled` or `enrollment.enabled` off never suspends anything.

The wire contract is the shared one: paths, bodies, statuses and error codes are specified in [`shared/service-auth/README.md`](../shared/service-auth/README.md#imperative-accounts-additions-to-v1) and are identical in Haystack and Manure. Summary: unauthenticated `GET /policy`, `POST /signup`, `POST /enrollments/inspect`, `POST /enrollments/redeem`, `POST /recover`; session-authenticated `GET /profile`, `POST /profile/{email,password,totp,totp-required}`, `GET /admin/users`, `POST /admin/users/{username}/{approve,reject,enabled,admin,reset}`, `GET /admin/enrollments`, `POST /admin/enrollments`, `POST /admin/enrollments/{enrollment}/revoke`. The boundary of this section applies unchanged (exact Host/Origin, no bearer credential, no query string, strict JSON at most16KiB, `Content-Type: application/json` and one `X-Account-Actor` on authenticated POSTs). Additional error codes: `totp-required`401, `pending-approval`403, `proof-rejected`403, `weak-password`400, `totp-mismatch`400, `username-unavailable`409, `rate-limited`429; every429/503 carries `Retry-After`. The five routes above keep their exact shapes; `POST /login` additionally accepts `{login,password,totp}`.

Chronicle specifics:

- **Identity.** An imperative user's id, login and display name are its immutable username (`^[a-z][a-z0-9_-]{2,31}$`). It has every right of a configured user (own archive, groups and invitations by id, `Ingest`/`Read`/`Raw` tokens through the routes above) and no other. `UserInfo{id,login,scopes}`, the WebSocket protocol and `chronicle.api` are unchanged; the dashboard reads the admin flag from `GET /profile`.
- **Projection.** `ch_users` stays the effective user directory. A newly active account (approval, signup without approval, redeemed invitation) receives its `ch_users` row and its `ch_owner_targets` row by plain insert in the activating transaction; later password changes and enable/disable update exactly that row. Pending applications have no row. Disabling an account disables the row (tokens gated, archive hidden from group members, sessions deleted); nothing is deleted.
- **Names are never reused.** Signup, invitation and approval refuse a username that equals, ASCII case-insensitively, the id or login of **any** `ch_users` row — configured, disabled, or removed from configuration but retained with its archives, memberships and tokens — besides the reserved names and configured ids/logins. A configured id or login that collides with an imperative account that has been active is a configuration fault: startup fails before writing anything, with the master switch on or off; choose another configured id/login.
- **Login.** A configured login is verified exactly as before. Any other login is decided by the imperative account: wrong password, unknown and disabled accounts answer the same `unauthorized` after one password verification; failed attempts are counted persistently (the failure is committed before the response) and back off. The legacy `POST /api/login` cannot carry a TOTP code: an account that requires TOTP at login is refused there as `unauthorized`; a pending applicant with the correct password gets `pending-approval`403 and a locked account `rate-limited`429 with `Retry-After`, as generated `Failure` bodies.
- **Limits.** While the switch is on, both login routes and the other unauthenticated routes are limited per client address (10 requests per minute per route class) and password work runs through two slots with a queue of16 (503 beyond). The client address is the socket peer, or the right-most `X-Forwarded-For` element when the peer is loopback (the local reverse proxy, which must set that header); without the header all proxied clients share one window.
- **Audit.** Signup, approval, rejection, enrollment, reset, recovery, lock, credential and admin changes are logged after commit as `account security event=… actor=… target=… outcome=… clientAddress=…`; no secret, e-mail address, code or request body is logged.

Authenticated settings/use refreshes cookie persistence. No account response/receipt/browser storage contains a generated bearer secret after the issuing response. The HTTP mint endpoint has no request-ID receipt or automatic retry: a lost acknowledgement is an **uncertain outcome**. Refresh the token list, identify/revoke the newly issued token and deliberately mint a replacement; never silently resubmit. Existing WS payload-bound receipt and replay semantics below are unchanged. Configured tokens are changed only through configuration reconciliation, not runtime revocation.

## WS operations
`Hello`, `Ping`, `Pong`, `Whoami`; reads `Search(SearchQuery)`, `GetSession`, `GetChunks(offset,limit)` (Result.Chunks: chunks,total,offset), `GetMessages(offset,limit)`, `GetRaw`, `Related(limit)`, `Facets(filter)`, `IngestStatus(offset,limit)`; browser-only mutations `RetryJob`, `MintToken`, `RevokeToken`, `CreateGroup`, `Invite`, `AcceptInvite(confirmSharing=true)`, `RemoveMember`, `LeaveGroup`, `DeleteGroup`, `Purge`, `Logout` (a token with OperateJobs reaches `RetryJob` and `ApplyRetryFailed` only through `POST /api/jobs/v1`); management `ListTokens`, `ListGroups`, `Receipt(mutationId)`. Result ADT branches are defined in model. Every request has UUID requestId; mutating receipts bind requestId to operation payload, changed replay conflicts. Mint returns secret exactly once; receipt lookup/replay returns token metadata with null secret (revoke/remint after uncertain outcome). Scopes `Ingest`, `Read`, `Raw`; Raw requires Read. Groups grant direct nontransitive read-only sharing. Owner must delete group rather than leave. Missing/unauthorized IDs indistinguishable. Search modes never silently degrade. Offset >=0, limits 1..100, transcript message page <=100 and cut by its byte bound (see "Oversize guards"); all results bounded. Receipt is Result.Mutation; errors Result.Error(Failure(code,message)).

MCP tools: `search_sessions` (query,mode lexical|semantic|hybrid, project/gitBranch/after/before/tags, limit/offset), `get_session` (sessionId), `get_chunks` (sessionId,offset,limit), `get_messages` (sessionId,offset,limit), `read_message_context` (sessionId,view,anchor,beforeBytes,afterBytes), `related_sessions` (sessionId,limit), `list_facets` (same filters), `search_tags` (required query; same filters; limit/afterTag), `ingest_status` (offset,limit), `whoami` (no arguments). Outputs share application generated result codecs inside MCP text content. `search_tags` reuses `Result.Facets` with only `tags` populated; its empty `projects` and `branches` arrays are intentional, not evidence those values are absent. The tag catalog itself requires no additional browser operation or model version.

## Ingestion
Source key = authenticated owner + collectorNamespace + discoveryRootId + format + producerSessionId + nullable subagentId; namespace persistent across collector restarts, discoveryRootId stable across root rescans. Owner is NEVER supplied. expectedRevision=0 for new source; CAS increments by one. Revisions are 32-bit: a source at revision 2,147,483,647 takes no further one, and `/api/ingest` or a part-upload open on it is 413 `too-large` before anything is written. requestId persists through retries; same payload same receipt, changed payload conflict. digest is SHA256 over UTF-8 file contents concatenated in files order (each file separately has sha256); files are relative logical paths, exact permitted JSONL UTF-8 bytes. Max defaults: 8MiB HTTP body, 16 files, 4MiB/file, 10000 messages. Messages preserve parent IDs, role and recordIndex referring to original JSONL record; display text follows the NUL projection below. Completion is Quiescent or Closed (not assistant-turn completion). Metadata missing fields null. No real source content in development tests. Upload acknowledgement means raw revision+durable job committed, not searchable yet. A newer archive head terminalizes unfinished older jobs as Failed/error `superseded-revision` and fences their workers, except a job that is Running with a valid lease: it keeps its claim (renewal, checkpoints, progress) and may publish the generation of its own revision; every other authority check (live owner, target/profile/epoch, live source, immutable revision binding, job/run/fence/lease) still applies. One job per source and profile runs at a time: the head job is not claimable while an older job is Running, becomes claimable when that job ends, and the next claim terminalizes an older job whose lease ended as `superseded-revision`. A job of an older revision never returns to the queue: a retryable failure or a large-job deferral that would requeue it ends it `superseded-revision`. Publication is monotonic: a job never replaces the published generation of a newer revision (it ends `superseded-revision` and its publication rolls back), so the default view is the newest published revision. A server start terminalizes every unfinished older job, Running ones included: their leases belong to the previous process. Older Complete jobs/generations remain available to pinned views. RetryJob for a superseded revision or obsolete model profile returns conflict, never a receipt for work that cannot run. Current-head AND current target-profile eligibility are checked under owner/target→source→job locks. A retained target that is not executable by this deployment rejects NEW ingestion and retry with `unavailable` before mutation; it is never silently queued under the new model's identity. A freshly authorized, payload-bound committed ingest receipt remains observable without an executable target. Collectors retain/retry pending uploads until a fresh confirmed owner rebuild establishes the current target. Startup preserves existing targets (including opaque targets inherited from pre-owner-target archives); only genuinely new configured owners seed current.

### Historian summary sources

`SourceFormat.Historian` uses this same ingestion, identity, revision-CAS, durable-job, indexing and read/ACL contract. One episode is one source within an approved destination/credential stream: an opaque `collectorNamespace` derived from that binding, journal UUID `discoveryRootId`, episode UUID `producerSessionId`, and null `subagentId` remain stable across its uploads. A changed destination or bearer starts a distinct source stream; an Ingest-only credential cannot establish owner continuity for reusing remote heads. Old queued work is never retargeted or backfilled. Producer-local episode revisions are distinct from the server's acknowledged archive revision.

The producer submits one normalized `historian` role message (`id=episode`, `recordIndex=0`) with the episode title, kind, status, claims with section/basis and citation references, and coverage notices. Raw `episode.jsonl` preserves the structured episode, generator metadata, claims and evidence references/metadata, never underlying evidence text bodies. These are historical model interpretations, not verified current state. The backend validates and stores generic JSONL/provenance; it neither parses a separate Historian domain nor follows evidence references. Archive/Activity format expressions and hints include `historian`; existing indexing policy, eligibility and authorization are unchanged.

### Oversize guards

A stored revision is bounded only by what stored it: one request (`maxBodyBytes`, up to 512 MiB) or a part upload (`maxFileBytes`, "Part uploads"); the reads and the indexing of a revision never hold more than these bounds:
- `GetRaw` of a revision whose raw files exceed `maxRawReadBytes` (UTF-8 bytes, known before anything is built) answers `too-large`; the bytes stay retained and exact, but `GetRaw` does not return them (the raw download endpoints do, "Raw downloads"). "A positive revision pins historical bytes" holds for every revision within the bound. The default bound equals `maxBodyBytes`, so nothing `/api/ingest` accepts becomes unreadable by default.
- A message page (`GetMessages`, MCP `get_messages`, which is also byte-admitted as before) holds the longest prefix of its at most `limit` messages whose stored values fit 64 MiB, and always at least one message while `offset < total`. A page holds fewer than `limit` messages before the end exactly when the byte bound cuts it: continue at `offset + messages.length` (not `offset + limit`); the end is `offset + messages.length == total`, never a short page. `total` is unchanged. The CLI reads every page of several messages: it accepts WebSocket answers up to 6 × 64 MiB + 1 MiB (403,701,760 bytes; the server's JSON escapes U+007F–U+009F in six bytes, which the jsonb measure counts as one or two) and MCP responses up to 7 × 64 MiB + 1 MiB (470,810,624 bytes), and refuses a larger answer — possible for a page of one message whose stored value alone exceeds 64 MiB — before reading more than its bound.
- Indexing holds one window of a revision at a time, whatever the revision's size (streamed indexing): a job reads its messages by position in short transactions, keeps each window's accepted annotation and embedding parts as its durable checkpoints (not in memory), and then publishes from those checkpoints in bounded committed batches into a staged generation that no read reaches, switching the source to it in one short transaction. `maxIndexingBudgetBytes` bounds one window and one message, not the job: a window whose pieces would hold more than `pieces · (8·d + 13312) + ContextSpans · 256` bytes (`d` embedding dimensions), or a message whose decode would take more than 7 times its stored text, ends the job `Failed` with error `index-budget-exceeded` and failure stage `Embedding`, terminally, before the window is embedded or the message fetched (a valid annotation that cuts its fragments into many pieces or Context spans; a message above `maxIndexingBudgetBytes / 7` bytes of stored text). No job is refused for the size of its revision. The job keeps its attempt count, is visible in `IngestStatus`, Activity and MCP `ingest_status`, and `RetryJob` reaches the same verdict until the budget or the dimensions change. Jobs that an earlier release ended `index-budget-exceeded` for their whole size stay so (nothing is retried automatically); `RetryJob` indexes them, and so does the source's next upload, which queues an ordinary job. A message above 8 MiB of stored text is fetched and decoded under the same one-at-a-time admission as a large ingest. One lane at a time holds the large-job permit, which a job of more than 100 windows needs: it shares lane time, not heap. A job's heap is bounded by its window, its decision (`annotation.maxResponseBytes`), one embedding part, one statement batch (at most 500 rows and 8 MiB), the carry between windows (at most 16 KiB of JSON) and the message being decoded (about 7 times its stored text while it is decoded, 2 times while a window stands inside it). The publication becomes visible only at its switch: before it, no search, Archive, Activity, tag or content read reaches the staged generation, and an explicit content view of it is `not-found`; a crashed or interrupted publication is continued by the same job's run, and one no run will continue is deleted by the background upkeep. After the switch the search rows of the replaced generation are deleted in bounded statements, and so are the derived rows of the generations an accepted explicit rebuild retires at that switch (their pins answer `indexed-view-retired` from the switch on); the background upkeep completes what a crash leaves; until PostgreSQL vacuums deleted search rows they cost semantic search time. The session stays readable and searchable throughout: pages, `LocateMessage`, context, Find and Archive search read stored rows and never decode it. `maxSmallJobBudgetBytes` is retired: still accepted (positive) so existing configurations start, it has no effect, and a server that finds it logs one warning at start.
- An append publishes only its tail (incremental publication): when a source's new revision continues the epoch of its published revision, the job indexes the windows from that publication's last window on and publishes them as the next version of its generation: a new generation (a new `ContentView` pin) that shares the earlier pieces, passages, spans and Context spans with the published one (their chunk and passage IDs persist across such revisions), and rewrites only the pieces of the passage open at that window whose metadata the new windows change: by default all of that passage's earlier pieces when its final summary or tags change, under a finite metadata horizon those of at most that many windows ("Problem-context passages"). It reads exactly as a full publication of the same content up to chunk and passage IDs; earlier pins read exactly as before. Limit: append publication work = the addition plus the passage still open at the cut (clone: p99 20 windows / 1,210 pieces, max 64 windows / 3,858 pieces); the open passage's pieces are written again when the new windows change its summary or tags. A full publication (a new epoch, a legacy revision, an explicit rebuild, `indexing.incrementalPublication` false, the first publication of a session published by an earlier release or under another `indexing.metadataHorizonWindows`) starts a new lineage. Server JSON `indexing` takes optional `incrementalPublication` (default true) and `metadataHorizonWindows` (1..2147483647, default 2147483647: every piece its passage's final metadata); neither is part of the index profile.
- Purge makes a source's content unreachable at its commit. Revisions stored per revision are deleted at the commit; the shared rows of revisions stored append-only (an epoch: messages by position, raw by byte offset) are deleted by the server's background upkeep within one pass (60 s).

### NUL display projection (all API ingesters)

Valid JSONL may encode U+0000 as `\u0000`. Raw file content, its SHA256, the source digest, and record provenance remain unchanged. Before archive persistence or any fragment/index derivation, each U+0000 in message text and human-readable metadata (title, project, gitRemote, gitBranch, gitCommit, producer, model, tags) becomes the literal six-character text `\u0000`. Tabs, newlines, other previously accepted Unicode controls and scalar Unicode remain unchanged. Transcript reads and all derived spans address these archived normalized UTF-8 message bytes, not decoded text from raw JSONL. Literal backslash escapes already in input are not changed; raw records are the fidelity source when these display representations coincide.

Source identity and receipt payload hashes bind the ORIGINAL request, before display projection. Retrying the same requestId and unchanged pending payload returns the exact receipt; changing original NUL text to a literal escape with the same requestId conflicts even when the display projection matches. No collector/spool rewrite, API version change, migration or reindex of previously accepted data is required.

U+0000 is unsupported in source/message/parent IDs, file paths, metadata workdir, digests, roles and timestamps and returns `invalid`/HTTP400 (existing format validations still apply). Unpaired UTF-16 surrogates in request strings are unsupported non-scalar Unicode and return `invalid` rather than reaching PostgreSQL (collectors from the part-upload release on replace them with U+FFFD in derived message text and metadata, leave raw content unchanged and refuse identifiers holding one locally). This does not reject other previously accepted controls in opaque IDs or POSIX paths.

### Part uploads (additive in 1.9.0)

For sessions above what one `/api/ingest` request carries. Bearer ONLY, Ingest scope, no query string, Origin as for `/api/ingest`; bodies and answers are the generated `UploadOpen`, `UploadPart`, `UploadLimits`, `UploadState` and `IngestReceipt`; every error is a JSON `Failure` with a non-2xx status. Every body bound is checked against `Content-Length` before the body is read and enforced while reading. Digests, chains and part hashes are lowercase hex; byte sizes are i64 (decimal strings on JSON).

- `GET /api/ingest/uploads` (no body) -> `UploadLimits`: the capability probe. A server without part uploads answers this path 404 without a `Failure` body; this API never does.
- `POST /api/ingest/uploads` `UploadOpen` (at most 64 KiB, or a smaller `maxBodyBytes`) -> `UploadState`. The open declares the complete resulting revision: `digest` (SHA-256 of the whole raw), `rawBytes`, `messageCount`, `messageChain` (message chain v1 of the stored messages), completion, redaction flag and metadata (each metadata string and `rawPath` at most 4,096 UTF-8 bytes); `base` names the head (its digest, raw bytes, message count and chain) for an append, which then sends only what follows the head. `requestId` with its declaration is the intent: replaying the same open answers its live attempt, after the commit its `Committed` state with the receipt, and after an expired, aborted or failed attempt a new attempt (`receivedParts` 0); another declaration under the same `requestId` is `conflict`. `expectedRevision` is the head (CAS, `conflict`); a `base` that is not the head is `base-mismatch` (no attempt). Declared raw bytes above `maxFileBytes` or messages above `maxMessages` are `too-large`. Another live attempt of the source, or 8 live attempts of the owner, is `upload-busy`.
- `GET /api/ingest/uploads/{id}` -> `UploadState`. An unknown attempt, or another owner's, is 404 `not-found` with a `Failure` body.
- `POST /api/ingest/uploads/{id}/parts` `UploadPart{ordinal,sha256,raw,messages}` -> `UploadState`. Ordinals count from 0: an accepted ordinal sent again with the same `sha256` answers the current state, with another `sha256` `conflict`; an ordinal beyond the next one is `conflict`. `sha256` = SHA-256(`chronicle.upload-part.v1` ‖ 0x00 ‖ u64be(UTF-8 length of raw) ‖ raw ‖ u32be(message count) ‖ m(x₁) ‖ … ‖ m(xₙ)) with m of message chain v1, else `invalid`. `raw` is whole JSONL lines (empty or ending with a newline), each non-empty line one JSON value; messages follow the rules of `/api/ingest`, `recordIndex` counts records over the whole revision (base included), and a `parentId` may name a message or raw record id of the base, of any part or of a later part (the commit requires all resolved). A part body is at most `maxPartBytes` (8 MiB); a part of exactly one record may be up to `maxLargePartBytes` (4 × `maxRecordBytes` + 1 MiB) with an announced `Content-Length`, and waits for admission like a large `/api/ingest` body (one at a time; 503 `unavailable` after 30 s, retry). A record — a non-empty line as `/api/ingest` counts records, split at LF, CRLF or a bare CR — above `maxRecordBytes` is 413 `record-too-large`, whose message names the record, its size and the limit; every other bound is 413 `too-large`. Among them, record counts and indexes being 32-bit: a revision holds at most 2,147,483,647 records, its base included, and the part that would pass that is 413 `too-large` before anything of it is stored, its message naming the limit and the count the part would reach (a record takes at least two bytes, so this needs at least 4 GiB of raw); an attempt holds at most ceil(`maxFileBytes` / 1 MiB) + 1,024 parts, and never more than 2,147,483,647; raw bytes are bounded for every `maxFileBytes` up to the largest i64. Neither adds a code, status or field: collectors see them as any other 413 `too-large` of a part. The lease, `expiresInSeconds` (3,600 s), restarts with each accepted part; after it parts and the commit are `upload-expired` (open again).
- `POST /api/ingest/uploads/{id}/commit` (empty body) -> `IngestReceipt`. The digest, raw bytes, message count and chain computed from the base and the parts must equal the declaration, every `parentId` must be resolved and every `recordIndex` below the record count; otherwise 409 `content-mismatch` and the attempt ends `Failed` (`UploadState.failure`), so send a replacement (no `base`) under a new `requestId`; an attempt that an earlier server staged past 2,147,483,647 records ends so too. An attempt that an earlier server opened at revision 2,147,483,647 ends `Failed` with failure `too-large` (413). Then the revision CAS and the switch: the revision, its durable job and its receipt become visible together, as for `/api/ingest`; a replay answers the same receipt.
- `POST /api/ingest/uploads/{id}/abort` (empty body) -> `UploadState`: `Aborted`, or the attempt's final state (`Committed` with its receipt when its commit won).
- Parts are durable when acknowledged but unreachable to every reader until the commit. The server deletes the staged content of attempts that ended (within a minute, in the background) and forgets them 7 days later; committed attempts are kept like receipts. Purge ends the source's live attempt first: its later parts and commit are 410 `gone`. `/api/ingest` on a source with a live attempt is 409 `upload-busy` (collectors before part uploads report it as `cas-conflict`).
- New statuses: `base-mismatch`, `upload-busy`, `content-mismatch`, `upload-expired` 409; `record-too-large` 413. Optional server key `maxRecordBytes` (default 33,554,432; 1,048,576..134,217,728); `UploadLimits.maxRawBytes` is `maxFileBytes`.
- **Deployment:** deploy this server before collectors with `uploadProtocol = "parts"`: a collector in front of an older server pauses its uploads, with nothing lost, until the server is upgraded or the collector is set to `uploadProtocol = "whole"`. Rollback: set every collector to `whole`, stop the server, run `scripts/down-025-uploads.sql` (read-only preflight, then `mode=apply` with the confirmation it names), deploy the previous server; revisions committed through parts stay.

### Raw downloads (additive in 1.9.0)

A revision's raw files of any size, in bytes, for the CLI and a browser's download manager. Browser session cookie ONLY, exactly as `GetRaw` (Read and Raw scope, which every browser session holds): no query string, no `Authorization` header (a bearer token, also one with Raw scope, is `forbidden`), at most one `Cookie`, `chronicle_session`, `Origin` and `Host`, `Host` the configured origin's authority, `Origin` optional (a download navigation sends none) but exact when present. Every error before the body is a JSON `Failure` (`Cache-Control: no-store`) with a non-2xx status, on every path under `/api/raw` (a server without this API answers 404 without a `Failure` body).

- `GET /api/raw/{sessionId}` -> `RawManifest` of the archive head at the time of the request; `GET /api/raw/{sessionId}/{revision}` -> `RawManifest` of that revision (decimal, at least 1). `RawManifest{sessionId,revision,files:[RawFileInfo{index,path,sha256,bytes}]}` lists the revision's files in their order from index 0, as `GetRaw` returns them. `sha256` is the lowercase hex SHA-256 of the file's bytes, `bytes` its size (i64, a decimal string on JSON).
- `GET /api/raw/{sessionId}/{revision}/{file}` -> the bytes of file `file` (decimal, from 0): 200, or 206 for a range, with `Content-Type: application/octet-stream`, `Content-Length`, `Content-Disposition: attachment; filename="chronicle-<sessionId>-r<revision>-f<file>.jsonl"`, `ETag: "sha256:<sha256>"` (strong: revisions are immutable), `Repr-Digest: sha-256=:<base64 of the SHA-256>:` (RFC 9530, of the whole file also on a 206), `Accept-Ranges: bytes`, `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`.
- `Range` (at most one header): exactly one range `bytes=FIRST-LAST`, `bytes=FIRST-` or `bytes=-SUFFIX` -> 206 with `Content-Range: bytes FIRST-LAST/TOTAL`, LAST clipped to TOTAL−1 and a suffix longer than the file meaning the whole file. A range with no byte in the file (FIRST ≥ TOTAL, a zero suffix, any range of an empty file) -> 416 `range-not-satisfiable` with `Content-Range: bytes */TOTAL`. Several ranges, another unit or any other syntax (LAST < FIRST included) -> 400 `invalid`. `If-Range` (at most one) not equal to the ETag -> the range is ignored: 200 with the whole file.
- Statuses before the body: 400 `invalid` (query string, malformed session id, revision < 1, file or range syntax), 401 `unauthorized` (no or expired session), 403 `forbidden` (bearer, foreign Origin or Host, ambiguous headers), 404 `not-found` (session, revision or file absent or not visible, indistinguishable), 416, 503 `unavailable` with `Retry-After: 5` when all four download permits are taken (a manifest takes none).
- The server pins the revision and file in one repeatable-read transaction, then reads the bytes in windows (4 MiB of an epoch revision, 16 MiB of any other), each in a short transaction of its own that checks the browser session, the session's visibility and the revision again, and reads the next window only after the previous one was written. Appends and replacements never change a pinned revision's bytes. A purge, a removed sharing, a logout or a disabled account stops the download at the next window; after the first byte any failure ends the response and closes the connection: the client receives fewer bytes than `Content-Length`, never other bytes. A permit is returned when the response ends, fails or the client disconnects. No resume beyond what `Range`/`If-Range` give a client.
- `GetRaw` is unchanged: below `maxRawReadBytes` it returns the revision whole, above it `too-large`; these endpoints have no size bound.

### Job operations for tokens (additive in 1.9.0)

A bearer token given the account-plane scope **OperateJobs** (with Read) can list its owner's indexing jobs, retry one and run Retry failed — nothing else. No existing token, configured default or migration has it: it is given to a configured token by naming it in `staticTokens[].scopes` (and removed the same way; reconciliation at start follows configuration) or chosen for a token issued in Settings / by `chronicle tokens mint` with the account header above. It is stored as `ch_tokens.operate_jobs`; typed values (`TokenInfo`, `UserInfo`, WS `ListTokens`/`Whoami`, MCP `whoami`, receipts) carry the token's typed scopes only, so a WS `MintToken` cannot request it.

`POST /api/jobs/v1`, body a generated `ClientEnvelope{requestId,operation}`, answer 200 with a generated `ServerEnvelope{requestId,result}`. In order:
1. no query string; `Origin`, when present, the configured origin; no cookie; `Authorization: Bearer`; `Content-Type: application/json`;
2. a credential without OperateJobs (unknown, revoked or disabled owner: 401 `unauthorized`) is refused 403 with exactly `{"code":"forbidden","message":"browser session required"}` — the answer a bearer gets for a mutation everywhere else — before the body is read;
3. one of 2 process-wide permits for the request's lifetime, else 503 `unavailable` "job operations busy" with `Retry-After: 5`;
4. a body of at most min(`maxBodyBytes`, 64 KiB) that decodes as `ClientEnvelope`, else 400/413;
5. the operation must be one of `ActivityJobs`, `RetryJob`, `PreviewRetryFailed`, `ApplyRetryFailed`; any other — including one added later — is refused 403 with the same body, before dispatch;
6. dispatch to the browser's implementation: ownership from the token's owner only (another owner's job is `not-found`), the owner's mutation lock, the payload-bound request-ID receipts (same ID and payload replay the stored result; another payload `conflict`), `Jobs.retry` eligibility and Retry failed's preview/selection-hash/`confirm` rules unchanged. A token's mutation re-checks, after the owner lock, that the token is still unrevoked with OperateJobs and an enabled owner (else 401). A stored Retry failed `conflict` is a `Result.Error` in a 200 envelope, as on the WebSocket; raised failures are `Failure` bodies with the usual statuses;
7. any other method or path under `/api/jobs/v1` is 404 with a `Failure` body. A server without job operations answers 404 without one.

Limits per owner (shared by all its tokens) and operation, in fixed 30-minute windows, in memory (a restart resets them; browser sessions are never counted): 120 `ActivityJobs`, 20 `RetryJob`, 6 `PreviewRetryFailed`, 2 `ApplyRetryFailed`. Each charge is one atomic per-owner, per-operation step taken before any effect — reads before their transaction, mutations only when they execute (an exact replay of a stored result is free) — and every fresh attempt counts whatever its outcome. A spent budget is 429 `rate-limited` "job operation limit reached" with `Retry-After` (seconds to the window's end); nothing ran, so it is definitive. A window opens at the first charge after the previous one ended: at most N per window, at most 2N in any 30 minutes.

The preview's answer counts the jobs Retry failed would re-queue (`counts.eligibleCurrentFailed`) and carries `X-Chronicle-Windows-To-Annotate: unknown`: the windows they still have to annotate are not computed (a Failed job keeps only its last run's window count, none when it failed before counting, and which windows reuse accepted work is known only once their content is windowed again).

Audit: the receipt row (`ch_mutations.token`) names the token that executed the mutation first (a replay never changes it; NULL for a browser session); after commit the server logs `jobs operation operation=<RetryJob|ApplyRetryFailed> owner=<id> caller=<token id> request=<id> replay=<true|false> actor=<token id|browser> outcome=<receipt|retried=<n>|<code>>`, no secret.

CLI: `chronicle jobs`, `jobs retry`, `retry-failed preview|apply` (and `rpc`/`call` with these four operations) use this route with `--auth bearer`; `auto` keeps the human session. A lost or unrecognized answer to a mutation is uncertain: run the same command with the same `--request-id` to read the stored outcome; it is never applied twice.

Password files contain PBKDF2-SHA256 string from password helper, DB/model credentials single-line files. Index execution uses only the configured current context-aware policy; there is no retained annotation-model registry or Legacy/P1 executor. Existing targets require a fresh confirmed owner rebuild, not automatic startup retargeting or a global maintenance switch.

`databaseLimits` holds the eight required database limits (`shared/service-runtime/README.md`), optional `requestConnections` and `backgroundConnections` (set together or omitted; the process's one connection pool, restart-robustness spec §5: omitted, `maxConnections` − 2 halved from `maxConnections` 8 up, e.g. 12 → 5 + 5, and below 8 one shared admission of `maxConnections`; set, request ≥ 1, background ≥ 3 and together ≤ `maxConnections` − 2; anything else is a `config` failure) and optional `startWaitMs` (default 120000, 1000..3600000; anything else is a `config` failure): `serve`, `serve-standby` and `migrate` wait up to that long for PostgreSQL to accept queries before they start, printing `chronicle database-wait code=jdbc-<SQLSTATE>` once when the wait begins and `chronicle database-wait ready seconds=<n>` when it ends; at the bound the start fails with `chronicle failure stage=database-wait code=jdbc-<SQLSTATE> error=JdbcFailure message="database-wait-timeout"` (exit 1). A refused login, an unknown database or a missing credential fails at once.

`accounts` (imperative accounts; absent = off): `{enabled, keyFile, signup:{enabled,requireApproval,maxUsers}, enrollment:{enabled,ttlSeconds}, issuer, reservedUsernames}`. `enabled` is the master switch and the only required member of a present object; it is never derived from the creation flags, and `signup.enabled` or `enrollment.enabled` without it is a configuration fault. Omitted members default to off: `signup.enabled=false`, `signup.requireApproval=true` (a self-registered account stays pending until an administrator approves it), `signup.maxUsers=100` (1..1000, counts every imperative row including pending ones), `enrollment.enabled=false` (administrator invitations; credential resets follow the master switch), `enrollment.ttlSeconds=86400` (300..604800), `issuer` = `Chronicle (<host of allowedOrigin>)` (1..64 printable characters without `:`; shown by authenticator apps), `reservedUsernames=[]` (refused in addition to the built-in reserved names). With `enabled=true`: `keyFile` is required, an absolute runtime path outside `/nix/store` holding the base64url encoding (43 characters, no padding) of 32 random bytes that encrypts TOTP secrets at rest; at least one enabled user must have `admin: true` (approval, enable/disable, admin flags and credential resets need an administrator, and a configured one is the break-glass path). `users[].admin` does not enable imperative account administration while the switch is off. An explicit `null` for any of these members is rejected. Rebuild and deploy the server before adding the object: an older binary ignores it.

## Error/close vocabulary
`unauthorized`: revoked/expired browser session or disabled user (terminal WS4401); `version-mismatch`: unsupported Hello versions (terminal4406); `protocol-error`: malformed text/frame/handshake or unexpected Pong (terminal4400); `forbidden`: request-level missing scope/browser-only denial (NOT connection-terminal); `invalid`: fields/pages; `conflict`: payload-bound receipt or revision CAS; `not-found`: missing OR unauthorized entity; `unavailable`: model/profile failure, never lexical fallback; `gone`: purged source; `indexed-view-retired`: an authorized exact generation pin whose derived payload was retired by an accepted explicit rebuild (nonterminal; never redirected); `range-not-satisfiable` (HTTP 416, raw downloads only): no byte of the requested range lies within the file. Exact Origin is checked BEFORE upgrading; same-origin absent/expired cookie upgrades then receives typed unauthorized plus4401 so browsers can distinguish authentication failure from network failure. Hello deadline10s, server Ping every20s with10s matching-pong deadline. Missing either liveness deadline closes with1013 (Try Again Later), which permits bounded automatic replacement after a pause or transient network failure; it is not a terminal protocol or authentication verdict. Malformed frames/unexpected Pong remain4400, revoked/expired credentials4401, and unsupported versions4406. Cookie expiry/revocation checked each operation and heartbeat. Authentication-store failures are availability failures (retryable WS1013), not evidence of expired credentials; only an actual unauthorized verdict closes with4401. Temporary reconnects clear protected views while checking the existing cookie rather than presenting them as a rejected login. A request-level Whoami failure offers an explicit session retry without requiring credentials.

Endpoint keys are FULL operation URLs, e.g. `/v1/chat/completions` and `/v1/embeddings`. Explicit empty credential files omit Authorization for unauthenticated local endpoints. An absent/unreadable file fails; there is no ambient-secret fallback. `secureCookies=false` is permitted ONLY with loopback listenHost and loopback HTTP allowedOrigin.

## Current indexing and durable accepted work (1.7)

Only `ContextAwareProblemsV1` is executable, and only its index profiles are read: registry rows of the retired policies `LegacyV4` and `ContiguousPassagesV1` remain solely as inert labels of retired generations and old jobs. The maximum-reasoning request policy retains `max_tokens=65536`, maximum reasoning and a 900-second operation deadline. Annotation `model-output` and exact `model-output/truncated` rejections share a durable limit of five per immutable window/input/retry epoch; each retry uses identical input and policy. Transport/deadline errors use the separate existing five-job-claim infrastructure limit, not local retries. Before calling the annotator, the worker durably reserves an authorization bound to job/run/retry epoch/window/input hash/fence. Cancellation or a response/commit crash may consume an authorization without a recorded rejection or an observed provider call. A ten-authorization backstop independently bounds unknown outcomes; the serial-window/five-claim invariant normally bounds the composition to nine. Rejections are recorded idempotently against their original reservation/fence. Exhaustion is terminal regardless of job claim count: `annotation-attempts-exhausted` for five rejections, `annotation-reservations-exhausted` for the authorization backstop. With server JSON `indexing.annotationContinuations` true (default false, read at start, part of no profile), a response that stops at a fragment boundary of its window is kept (reason `annotation-partition-continued`, one of the five; the fifth non-final response ends the window even then, and one whose rest would exceed the request bounds is rejected `annotation-continuation-unrequestable`): the rest of the window is requested from that fragment on, with the carry after the kept parts, and the stored decision is still one complete partition. Kept parts are committed with their authorization before the rest is requested and are resumed by later claims only after validation against the window's own authorization rows and active chain; anything else is discarded and the whole window requested. A window whose authorizations were reserved for another input then fails the job `annotation-input-changed`, terminally. With it false, every response that does not cover its window is rejected `annotation-partition-incomplete`, nothing of it is kept or resumed, and the whole window is requested again. `index-budget-exceeded` (the indexing budget, "Oversize guards") is terminal in the same way. Accepted checkpoint reads and local state reconstruction never spend or retry the provider budget.

The annotator explicitly partitions every nonempty normalized source scalar into `Problem` or `Context` using canonical half-open fragment/Unicode-scalar coordinates. A provider point written at a fragment's scalar count is read as the next fragment's offset 0 and stored canonically. Windows contain at most64 fragments of at most2048 UTF8 bytes. Substantive domain facts, decisions, parameters, ownership, outcomes and rejected factual alternatives are Problem material even without an explicit question or imperative; Context is non-task runtime/bootstrap/heartbeat/tool-inventory material. Context has exactly kind/start/end: no invented summary, tags, problem ID or vector. Only real Problem slices become exact-source retrieval pieces; pieces never join distinct messages or bridge omitted Context. Context advances the original cursor without closing an open problem, and continuation may refer to a problem opened earlier in the same window. System/developer/subagent role or bootstrap-looking prefixes are not blanket exclusion rules. Empty/context-only sessions can publish a complete, zero-problem generation without embedding calls.

Carry contains only bounded existing-problem information: original/updated summaries, tags and at most4096 source bytes/16 fragments. **No Context text is buffered across windows.** Thus antecedents solely in an earlier Context window are not supplied as semantic carry; this is an explicit bounded-quality limit, not deletion of archived source. Every normalized message byte and original position remains available to revision-only reads and selected-history Find. Publication validates the exact once-only Problem-piece/Context coverage union.

Metadata horizon: a retrieval piece produced in window k carries its passage's summary and tags as they stood after window min(k + H, the passage's last window), H = `indexing.metadataHorizonWindows`. The default, H = 2147483647, gives every piece its passage's final summary and tags. A finite H is opt-in; its effect on real-model relevance is not measured (scripted mechanism result only: reports/ingest-c/REL/RESULTS.md); on the clone it would save ≈ 2 % of append work. It bounds what an append writes again within a long open passage: the pieces of a passage longer than H + 1 windows, except those of its last H + 1 windows, then carry the summary and tags the annotator held H windows after them, not the final ones, so lexical and hybrid search, Related, tag filters, facets and the tag catalog see that intermediate vocabulary for them (vectors embed the piece text only and are unchanged). Passage rows (`GetPassages`) carry the final metadata. The generated tags of a publication (facets, tag filters, the tag catalog) are its pieces' tags. A changed H applies to a session from its next publication (a full one); generations published earlier keep their rows.

Transient database failures (restart robustness, no wire change, 1.9.0): a statement cut by its timeout, a lost or refused connection while the database starts, stops or is full, a full admission, or a lock timeout at the start of a publication while a statement of an earlier attempt of the same job still runs is not charged to a job's attempts. The job stays `Queued` with `JobInfo.error` `database-transient` and its `failureStage`, held until `ActivityJob.leaseExpiresAt` (its next attempt; `leaseActive` false; the `lease` filter value `inactive`), 1, 2, 4, 8, then 15 minutes after each consecutive one; the 10th in a row ends it `Failed` with `database-transient`. An attempt that commits progress starts the count again; `RetryJob`, retry-failed and a rebuild reset it. The worker writes the hold while the attempt's lease lasts, each try within one 4.5 s deadline (a try cut during its commit is read again, never written twice), so a PostgreSQL restart that ends at least 45 s before the in-flight job's lease ends charges no attempt, provided no other transaction holds that job's rows; longer outages charge one attempt through reclaim and can lose one paid model answer; crashed jobs resume as today. The 45 s assume PostgreSQL in the same pod (logins before it is ready fail at once) and that the records do not queue behind long background work on the shared connections (right after a restart the interrupted publications are themselves held for at least 1 minute); both are stated with the derivation in docs/operations.md, "Publication after a database restart". A publication's statements run under `indexing.publicationStatementTimeoutMs` (default 300000, at least `databaseLimits.statementTimeoutMs`, at most 3600000); every other transaction keeps `databaseLimits`. With `databaseLimits.maxConnections` of 2 or more one connection is kept for lease renewals (with 1, one admission for everything, as before).

A job run UUID persists across automatic reclaim and Failed retry; a Complete job's retry or a confirmed owner rebuild rotates it. A new run reuses accepted work of earlier runs of the same source and profile: a window whose source fragments (with their message positions) and carry equal an earlier run's accepted input takes that decision, and an embedding batch of equal texts that batch's vectors, each by a reference to the exact accepted checkpoint, which publication and resume read (never a new lookup). After an append only the windows from the previous revision's last one on are annotated; a Complete job's retry is a cached republication of its revision (no model call). A run of a confirmed owner rebuild reuses no other run's work: it calls the models for every window, which is how accepted annotations are replaced; within its own run it resumes from its checkpoints like any run. Single-job and bulk Failed retry advance a separate annotation retry epoch without deleting prior reservation evidence or accepted outputs. Automatic reclaim never resets either window budget. Legacy Failed jobs are not retried at startup. Drain old workers before cutover; old binaries cannot enforce the new budget. Validated annotation decisions and each accepted exact-source embedding batch are durably committed before later work. Keys bind run, profile, logical immutable revision identity, algorithm, exact input and bounded carry. Opaque JSON TEXT preserves scientific numeric lexemes and negative zero. No accepted output is silently replaced or treated as a cache miss on corruption/input mismatch. Every get/put and final publication rechecks owner, target/profile/epoch, source, job/run/fence and lease; stale authority is denial. The logical revision binding survives logical backup/restore, unlike physical xmin; normal snapshot/identity UPDATE is prohibited. Claim-local immutable snapshot bindings avoid full-source serialization on each checkpoint. No global mutable source cache is used.

There is no exactly-once provider-call claim across response/commit crashes: only committed accepted work, and (with `indexing.annotationContinuations`) a window's committed kept parts, are reusable. Rejection diagnostics use typed stable reason tokens and bounded numeric/enum structural fields, never transcript text, summaries, tags or rejected values. Annotation call telemetry records provider usage before decoder validation; an HTTP-success response rejected by the annotation decoder counts as a failed annotation call while retaining observed usage. `JobInfo.failureStage` is required-present nullable Annotation/Embedding/Publication; unknown historical stages remain null. Failed retry retains the prior error/stage; supersession or lease exhaustion replaces it with an unknown stage, and completion clears it.

## Explicit fixed-current owner rebuild (1.7)

`PreviewOwnerReindex` and confirmed `ApplyOwnerReindex` bind an exact owner selection hash, current destination and request receipt. They force replacement of ALL selected live HEADs, including already-current and Running work: `alreadyCurrent=0`, replacements/queued equal selected heads. Each replacement annotates and embeds every window again, also into an unchanged profile (no accepted work of earlier runs is reused). Each accepted intent rotates target epoch and runs; stale previews conflict. There is no unsafe global maintenance CLI, implicit boot retarget or old-model fallback.

`GetReindexStatus(requestId)` returns targetProfile and a finite captured cohort: total, complete, superseded, failed, pending are i64 values, exclusive and summing to total. Future HEADs never enlarge it; purge/job deletion cannot shrink it. Recorded exact-member completion survives later revisions and run rotation. A member whose job is still Running with a valid lease after a newer revision is pending, not superseded: it may still complete.

Old publication/search stays intact until validated atomic replacement and final live-lease acceptance. Then all obsolete derived generations for that selected source are retired; raw data, normalized revisions, receipts and job IDs are not deleted by rebuild. Retirement consent is ONE-SHOT per captured source/target epoch/profile, separate from exact revision/job/run completion: a validated superseding revision may fulfill retirement while its captured member remains Superseded. Later ordinary publications preserve the new current-policy history unless another explicit rebuild is accepted. Publication rollback also rolls back completion/retirement markers and all derived changes.

Retired full-generation pins first reauthorize, then return exactly `indexed-view-retired`, never redirect to HEAD. A valid, authorized indexed view hidden by the owner's indexing preference returns `indexed-view-disabled` instead of redirecting. Clients may offer to open the same revision without the generation, but must not do so automatically. Revision-only views, Find and raw revisions remain available. The old publication formats exist only as such retired generations (see "Published generation format"); removing old wire codecs does not remove raw revisions.

`GetChunks` / MCP `get_chunks` pages every published annotation in deterministic original source order, never UUID order. Read scope and live same-session ACL apply before limits. Count+rows use one REPEATABLE READ transaction and captured generation pointer; concurrent publication cannot mix generations within one page. GetSession retains its first100chunk compatibility response.

## Immutable content views (final v1 freeze)
`ContentView{revision:i32,generationId:UUID|null}` identifies immutable source content and optionally its immutable annotation generation. `SessionInfo.view` identifies the content supplying its metadata; `SessionInfo.revision` remains the current archive HEAD, and `indexedRevision` remains the current published source revision, so indexing lag stays explicit.

GetSession/GetChunks/GetMessages have an appended `view:ContentView|null` selector. Null is discovery: resolve current published view, or archive head without annotations if never published. Clients MUST retain the returned `SessionInfo.view`, `ChunksResult.view`, or `MessagesResult.view` and send that same view on all subsequent source/chunk pages. A non-null view with null generationId explicitly selects raw/normalized archive-only content for that revision, with no annotations. A generationId must belong to exactly that session and revision; mismatches and unauthorized historical views return not-found. Revisions remain immutable and retained until owner purge. Generation identities remain retained, but an accepted explicit rebuild may retire obsolete derived payloads; full retired pins return `indexed-view-retired` after fresh authorization. Ordinary later publications do not retire historical generation payloads. Reannotation of the same source creates a different generation pin.

Other MCP tool arguments are unchanged.

## Indexed search and count scope (1.1)

`SearchResult{hits,total,countScope:SearchCountScope,rankingLimit:i32|null}` adds `SearchCountScope` (`ExactMatches` or `CandidateWindow`). Lexical search uses an indexable `document @@ websearch_to_tsquery` GIN predicate, exact authorized matching-session `total`, `ExactMatches`, and null rankingLimit; an empty query browses eligible published sessions.

Semantic search obtains at most1000 authorized, filtered chunk candidates through HNSW. Hybrid unions that ANN leg with at most1000 independently authorized lexical candidates, then applies RRF(k=60). Both modes exactly rerank retained candidates using their original full-precision PostgreSQL vector cosine distances; candidate discovery remains approximate. `total` is the exact number of distinct sessions in that candidate window, NOT the global eligible-session/match count. `countScope=CandidateWindow` and `rankingLimit=1000` (semantic) or2000 (hybrid) expose this boundary. rankingLimit bounds chunk candidates before session deduplication, not the number of hits or an assurance that the window fills. Offset must be smaller than rankingLimit; otherwise `invalid`. Pages still return at most100 sessions and offsets beyond the actual candidate-session total return empty. Search pages are not a frozen search snapshot across requests; live ACL/publication changes may change membership/order. Facets remain exact distinct-session counts over their authorized filtered published corpus, not the ANN window.

Exact ties (equal cover density, equal distance, equal fused score) are ordered by session, the chunk's place in its session (unknown for rows published before it: last), then chunk ID, in every mode. Current Hybrid recomputes lexical and full-vector ranks over the candidate union, then selects each session's best fused chunk. A candidate receives lexical RRF credit only when its document satisfies the full `@@ websearch_to_tsquery('english', query)` predicate; a positive cover-density score alone is insufficient. Nonmatching ANN candidates remain eligible for the vector term, but receive zero lexical score before lexical rank assignment. In particular, lexical exclusions are not hard semantic filters.

Live ACLs, owner/reader enabled state, profile identity, published-generation equality and all structured filters apply before EACH candidate LIMIT. pgvector strict iterative scanning continues beyond rejected tuples (ef_search200, max_scan_tuples200000, scan_mem_multiplier4), and every rejected index entry spends that budget: other owners' or filtered-out rows, and rows of generations being published or retired and not yet vacuumed. A semantic leg (Search, each Archive operand) that returns fewer chunks than min(1000, its visible set) is short: the server counts the visible set (bounded) only then and runs the leg again in the same snapshot — ranked exactly by full-precision distance when the visible set holds at most20000 chunks, otherwise by a wider iterative scan (max_scan_tuples1000000, scan_mem_multiplier64, at most5s). A leg still short then fails the request with `unavailable` and the message `semantic candidates incomplete: …` (retry later, narrow the filters or use lexical mode); Hybrid fails as a whole, never a silently partial or lexical-only window. A full leg remains approximate. There is no unbounded application postfilter of a global topK and no unauthorized count contribution. Full vectors remain `vector`; HNSW uses normalized `halfvec(dimensions)` expression indexing, including2048-dimensional models. Literal dimension and partial-index predicates match even under generic prepared plans.

There is no API-version-based exact search path or compatibility fallback. MCP and the dashboard use the same current result shape, including scope metadata. The exact search oracle retained for diagnostics is not a negotiated API.

Structured tag filters apply AND across requested tags, with each tag allowed in the union of published-source metadata tags and ANY chunk's generated work tags for that same session/generation. Facets use the same published revision and live ACL; tag counts are DISTINCT sessions, not chunk occurrences. Pending mutable-head metadata never labels an older published search generation.

`search_tags` searches tag names, not conversation contents. Required `query` is a literal substring; `""` browses all matching tags. Matching uses PostgreSQL `lower(... COLLATE pg_unicode_fast)` on both operands: case-insensitive Unicode-lower matching, not fuzzy search, wildcard/Boolean syntax, normalization, accent removal or full Unicode case folding (`ß` is not `ss`). Whitespace, `%`, `_`, quotes and backslashes remain literal. Exact case-distinct tag values remain separate entries and counts.

Pages contain 1..100 maximum requested entries (`limit`, default20), ordered by the exact tag value under `COLLATE "C"`, not by popularity. Continue with `afterTag` equal to the last returned `value`, exclusively; stop when `tags` is an empty array. An empty tag value is legal, so preserve `afterTag:""` rather than treating it as an absent position. Positions need not still exist and confer no authorization. Query length is at most2048 UTF-16 units; the copied position has no smaller tool-specific length cap than existing request budgets, so historical long tags are not stranded by an arbitrary query-length limit. Query and position require valid Unicode scalars without NUL.

Every page reevaluates current published revisions, structured filters and live authorization; unpublished heads, superseded generations and unauthorized sessions do not contribute. Shared source/generated tags count once per session, not per annotation. Returned counts retain the generated `Facet.count` signed-i32 contract; out-of-range counts fail explicitly rather than wrap. Read scope suffices; Raw/browser privileges and model/embedding readiness are not required. The in-dashboard model adapter uses the same parser and query with source-byte admission before selected payload decoding, bounded to the requested page; ordinary public MCP retains its existing request/response policy. Existing argument/read budgets can reject oversized requests or pages explicitly—no truncation or silent omission. The row bound does not bound aggregate SQL work. Pages are live, not snapshot-pinned: complete enumeration assumes a stable authorized dataset; concurrent inserts before a position may be missed and counts or visibility may change.

Example: `tools/call` with `{"name":"search_tags","arguments":{"query":"postgres","limit":20,"project":"ponygirls"}}` returns generated `Facets.result.tags` entries such as `{"value":"PostgreSQL","count":3}`. Nonempty returned values of at most128 UTF-16 units can be used unchanged in `search_sessions.tags`; that existing filter still rejects empty or longer historical values even though the catalog exposes them. Pass the last value, without truncation, as `afterTag` with the same query/filters to continue. `list_facets` remains the separate top100/popularity tool.

### Claim order in Activity (additive in 1.9.0: two new operations)

Why a job is not running and where the claim order in force puts it (indexing claim-order spec §7), in operations of their own: the replies of `Activity` and `ActivityJobs` (and every other existing operation) are exactly those of the release before — an older client validates their exact fields (the CLI: `cli/src/wire.ts` exact key sets) and negotiates only `1.9.0`. Everything is evaluated on the stored rows at the read's observation instant (`observedAt`, microsecond precision: lease flags, reasons, candidates and ranks all at that instant) with the scheduler's own predicates.
- `ActivityClaimOrderSummary{}` → `Result.ActivityClaimOrderSummary{result:{observedAt,queue:ActivityQueue}}` — the viewing owner's own current unfinished jobs only: `claimOrder` (`SourceId`/`Waiting`), per class `fresh`, `bulk`, `unclassified` an `ActivityClassQueue{queued (any waiting reason), claimable (candidates), held, awaitingReclaim (`AwaitingReclaim` + `LeaseExpiredAwaitingReclaim`), oldestWaitingSince}`, `awaitingLarge` (own jobs waiting for the large-job lane/permit) and `largeAhead` (the rank of the first of them).

- `waitingSince` (ISO-8601, when the job joined its order: upload, single retry, retry-all apply, rebuild; kept through claim, sizing, deferral, back-off and reclaim; a finished job keeps the value of its last wait), `bulk` (`true` retry-all and rebuild, `false` uploads and single retries). Null on a row an older release wrote: an unfinished one until this release's next start (the start fill classifies every unfinished job; `reseed-claim-order` redoes all), a finished one for good. Shown whatever the claim order.
- `waiting: ActivityJobWaiting` — null for a job that is not current (older revision, other profile), finished, or running (Running, lease valid, current indexing epoch). Otherwise, first match: `IndexingOff` (the owner's indexing is off, or its retained target is a profile this deployment does not execute — the read answers, no rank); `AwaitingReclaim` (Running attempt invalidated by an indexing-policy change); `RunningWithoutLease` (Running with no lease: no claim compares it, no cleanup ends it; `RetryJob` requeues it); `LeaseExhaustedPending` (Running, lease ended, attempt limit reached: the next claim ends it `lease-exhausted`); `LeaseExpiredAwaitingReclaim` (Running, lease ended: never reported as running); `Held{nextAttemptAt}` (Queued with a future attempt time); `BlockedByOlderRevision{revision}` (an older revision of the source and profile Running with a valid lease and a current indexing epoch — one whose lease ended or epoch moved does not block: the claim supersedes it first); `AwaitingLargePermit` (claim order `source-id`) / `AwaitingLargeLane` (`waiting`) for a job deferred to the large-job lane; `Queued` (claimable).
- `ahead: i64` — for a job a claim may take now (by the claim's predicates: claimable and not blocked): its rank, the NUMBER of claim candidates of all eligible owners (enabled, indexing allowed, target profile claimed, head job of a live source) that the order in force takes before it. A count only: no id, title, owner or other attribute of another owner's job appears in any response. `waiting`: a sized job — among sized candidates (the large-job lane's order); a fresh or bulk job — among the unsized candidates of its class (the order every lane takes that class in); both by (`waitingSince`, source id); an unclassified job: none. `source-id` (owner id, then source id): with one lane (`annotationSessions` 1, the permit at every claim) every candidate over all; with more lanes only a job the large-job permit is needed for (sized, or more than 100 windows), over all — any other job is taken by lanes with and without the permit, whose orders differ: none. An order, not a time estimate: older work that returns (a retry after its back-off, a reclaimed lease) moves ahead again.
- An older server does not answer the dashboard: each server serves its own dashboard. Clients of the existing operations (an older CLI) are unaffected; `chronicle rpc`/`call` of this tree can send the two operations (no command uses them).

### Relevance preference and live ordering (1.8)

`ArchiveQuery` appends required `preferRelevance:bit`; `ArchiveResult` appends
required `relevanceOrdered:bit`. The server applies relevance only when the
preference is true and the parsed expression has at least one distinct positive
text operand under even NOT parity. Otherwise it applies the requested existing
`sort`/`direction`; this is an explicit preference contract, not a model fallback.
The result reports which ordering was applied. Empty, metadata-only, mode-only
and negative-only queries retain column ordering. Negative-only Semantic/Hybrid
membership still requires the same embeddings as before.

The dashboard initially requests this preference, retaining LastTimestamp Desc
as its browsing tuple. A deliberate column sort disables the preference and
remains sticky across text/mode edits, refresh and same-owner reconnect. The
explicit relevance action reenables it without losing the remembered column
order; clearing text or submitting metadata restores that tuple. Ordering intent
is account-scoped tab memory, not persistent browser storage. Consumers must
validate the returned Boolean: the pinned generated TypeScript primitive casts
alone do not reject an absent or incorrectly typed field.

Boolean membership, HEAD substring fragments, published ANN candidate sets,
authorization and `matchedView` provenance are unchanged. For every distinct
positive text operand, Lexical/Hybrid literal membership contributes `1/61`.
Semantic/Hybrid contributes `1/(60+rank)`, where SQL `rank()` orders sessions by
their nearest original full-vector cosine distance among that operand's same
bounded ANN candidates. Chunks are deduplicated into sessions before ranking;
equal distances share a rank. Sum contributions as PostgreSQL numeric, then order
by score descending, last message time descending with nulls last, and UUID
ascending. Negative operands contribute nothing; rows admitted only through
metadata/negative branches remain with score zero. Literal HEAD membership stays
unbounded, including stale or unindexed heads beyond the ANN chunk limit.

Literal evidence is binary, not a graded full-text score. Lexical AND matches
can all tie and therefore retain recency order; OR can reward matching more
operands. Semantic noise is ordered, not removed. RRF scores are not confidence
and have no acceptance threshold. Dashboard HEAD substring/per-operand retrieval
remains distinct from MCP's published-passage websearch/RRF algorithm.

Column ordering retains version2 opaque cursors. Relevance uses version3 with
exact numeric score text and nullable timestamp, binding the exact expression,
reader, requested column tuple and UUID. Mixed ordering versions and malformed
numeric positions fail before embedding calls. Counts retain their existing
retrieved-set scope. These are live keysets, not search snapshots: publication,
ACL, ANN or query-vector changes can shift ranks and cause duplicates or omissions
between pages; client deduplication does not guarantee complete enumeration.

Both relevance flags are required in the current wire format; missing flags do not receive compatibility defaults. All column enums, limits, model failures and query language remain unchanged. No migration, embedding/profile change or reindex is required.

ArchiveRow.head.view is archive-only HEAD; publishedView and matchedView are
separate immutable pins. A representative matchedView does not prove that every
Boolean term matches the same revision. Both dialog panes must retain the same
selected pin, with an explicit latest-HEAD switch. LocateMessage resolves a
message's position within that required pin without scanning previous pages.

Activity is owner-only. Current HEAD/target-profile jobs and all historical jobs
are counted separately. Running state is not an active lease: active, expired and
unleased Running counts remain distinct. retryable is Current AND Failed, while
the legacy RetryJob fencing behavior is unchanged. Absent collector reports are
unknown; freshness refers to actual report receipt, not a socket connection.
All summary totals are i64 decimal strings on JSON / bigint in TypeScript.

Migration006 adds normalized per-revision info, message and bounded literal
projections plus generation tags. Backfill uses committed batches of4 revisions,
streamed message reads and transactional projection writes, without loading raw
files into JVM listing paths or calling models. Source normalization, annotation
policy and semantic profile identities are unchanged. pg_trgm1.6 is bundled in
the pinned PostgreSQL18.6 and can be installed by a non-superuser database owner.

## Selected-history message find (1.6)

`SearchSessionMessages(sessionId:UUID, view:ContentView, literal:str, cursor:str|null, limit:i32)` requires Read scope and an explicit immutable view. `Result.SessionMessageSearch` wraps `SessionMessageSearchResult{view:ContentView,hits:MessageSearchHit[],nextCursor:str|null}`; each hit is `{messageId:str,position:i32}`. No snippet, message body, exact total, regex or model request is returned or performed. Use existing `LocateMessage` and `GetMessages` with the same pin for navigation. No new MCP tool is registered.

The server matches all archived normalized `message.text` values in exactly the selected session/revision, including unindexed revisions. It does not search raw records, annotations, metadata, Archive fragments, loaded pages or current HEAD. The complete selected view (including optional generation) is validated and echoed, although text is revision-scoped. `ContentView(revision,None)` never follows HEAD. Owner/reader enabled state, current direct sharing and non-tombstoned source authorization are checked together with view validation in each page's repeatable-read transaction; cursors grant no access.

Matching uses PostgreSQL `strpos(lower(message.text COLLATE pg_unicode_fast),lower(literal COLLATE pg_unicode_fast))>0`: case-insensitive literal matching with database-collation semantics, not universal Unicode casefold. Percent, underscore and backslash are literal characters. Unicode, emoji, tabs and other accepted controls are preserved; a literal U+0000 query uses the same `\\u0000` display projection as archived text. One locator per matching message is returned in stable normalized source-position order, using position keyset pagination with limit+1 lookahead after matching.

The database measures the limited locator selection and charges it before fetching/decoding IDs, even for unrestricted browser reads; an admitted caller's source budget is also charged. Budget excess fails explicitly with `read-budget`, never silent truncation. Each database statement has a five-second deadline (or a stricter existing deadline), including authorization, lock waits and preflight; cancellation fails with `deadline`, never no-matches or partial success.

Opaque base64url JSON cursors bind reader, session, full view, matching policy, exact query digest and last position, and are HMAC authenticated by the stable archive reader instance. Mismatch/tampering is invalid. Restart/replacement of that instance invalidates outstanding cursors; restart the find from its first page. No cursor authenticates a reader or overrides fresh authorization. APIs1.0–1.5 remain frozen, available and unchanged.


## Byte-bounded message context (1.9)

`Operation.ReadMessageContext{sessionId,view,anchor,beforeBytes,afterBytes}` returns
`Result.MessageContext{result:MessageContextResult}`. `MessageContextResult` carries
`sessionId`, the exact `view`, a resolved `anchor:PassageSourceSpan`,
`excerpts:ContextExcerpt[]`, and nullable `previous`/`next:Span`.
Each excerpt is `{source:PassageSourceSpan,role:str,text:str}`; source carries
`messageId`, `messagePosition`, `start`, `end`. There is no whole-message or raw
payload, parent ID, timestamp, snapshot, or synthesized text separator.

MCP `read_message_context` requires exactly these five arguments:

```json
{"sessionId":"00000000-0000-4000-8000-000000000001","view":{"revision":1,"generationId":null},"anchor":{"messageId":"m0","start":0,"end":12},"beforeBytes":2048,"afterBytes":2048}
```

Copy `session.id`, the complete `session.view`, and one `chunk.spans` entry from
a search hit. The existing search/session/chunk/span shapes are unchanged; a
multi-span chunk permits independent navigation from each span. Unlike older
MCP content tools, this tool requires a nested `view` with both fields present
(`generationId` may be null). Unknown/missing fields are invalid. Read scope is
sufficient; browser/Raw scope, indexing work and model requests are not needed.

Offsets address archived normalized UTF-8 bytes, half-open, on Unicode-scalar
boundaries: `0 <= start <= end <= message UTF-8 length`. A zero-width anchor is
valid, including at a message boundary. The anchor is included in full and may
not exceed2048bytes (`read-budget`); it is never silently clipped. Each required
side budget is zero (direction disabled) or4..2048bytes. Positive budgets admit
any Unicode scalar, not necessarily a grapheme cluster. Expand first within the
anchor message, then into at most four adjacent messages per side. Stop at the
first scalar that does not fit remaining bytes; do not skip it. Encountered
empty messages count toward the adjacency cap. Omit a nonempty neighbor when
no scalar fits; keep continuation at the preceding returned boundary. The
anchor itself is always retained, including when zero-width. Return at most nine excerpts in
source order, with the anchor message merged once and original roles/boundaries
preserved. Every excerpt's UTF-8 bytes equal exactly its source slice; no text
separators are injected.

`previous`/`next` are zero-width spans at the outer returned boundaries, nonnull
iff bytes or messages remain in that direction. Continue with that anchor and
the exact same session/view, setting the other direction to zero. At a message
start/end, navigation proceeds into the neighbor. Empty sequences advance by
position. Boundary metadata can repeat, but continuation never repeats text.

`PostgresArchive` delegates to its private `PostgresContextReader`, with one
REPEATABLE READ source transaction, fresh same-session ACL/pin validation and a
five-second per-statement deadline (preserving stricter configured deadlines).
Direct numeric message location, byte lengths and scalar-boundary projections
are bounded; only bounded exact-source excerpt text is selected. Complete
selected JSON framing/metadata is measured and admitted before text transfer to
the JVM. The endpoint always applies a cumulative64KiB source cap, including
numeric source projections and excerpt framing, even with an unrestricted
caller; admitted callers additionally consume their own cumulative budget.
Generated serialized `Result.MessageContext` and the complete MCP tool-content
wrapper (including its additional JSON string escaping) are each capped at128KiB. These are
conservative initial resource limits, not measured semantic sufficiency.
PostgreSQL may inspect/decompress full stored text internally: this bounds
application transfer, not database CPU independently of source size.

Public HTTP supplies explicit fresh bearer authentication before and after this
new read and compares the captured global security epoch. Browser API1.9 uses
fresh `currentBrowser` and the same epoch policy. Live MCP tester calls retain
fresh captured-run authority through `ReadAccess.blocking`. The old two-argument
MCP handler cannot invoke context without explicit fresh authority; the nine
older tools retain their former behavior. Source ACL/pin validity is checked
in the source transaction's snapshot; credential/epoch checks are delivery
checks, not a second source snapshot. Global epoch changes can conservatively
deny an unrelated context read. No final check can prevent revocation occurring
after that check or retract a previously delivered result.

Malformed ranges, scalar cuts and side budgets return `invalid`; absent,
unauthorized or purged source/message/view returns `not-found`; an authorized
retired generation returns `indexed-view-retired`; source/caller/result limits
return `read-budget`; SQL cancellation returns `deadline`. The one-shot MCP
runner retains named `deadline` and `indexed-view-retired` failure codes with
a generic sanitized message and no automatic retry. Ordinary append or
republication preserves old full pins; foreign session/revision generations
never fall back to HEAD. APIs1.0–1.8 signatures/codecs remain frozen, and reject
the new operation/result branch explicitly rather than fabricating compatibility.

## Archive-expression source cards (current 1.9)

Browser `Operation.ArchiveSearch{query:ArchiveQuery}` returns
`Result.ArchiveSearch{result:ArchiveSearchResult}`. The result contains the exact
shared `page:ArchiveResult` and one ordered `ArchiveSearchEvidence{sessionId,matches}`
per page row. Existing `Operation.Search`, `SearchQuery`, structured `SearchFilter`
and all MCP tools are unchanged; no Archive-expression MCP tool is added.

The application shares Archive expression parsing, validation and per-operand
query embeddings with ordinary Archive browsing. One shared PostgreSQL kernel
implements both paths: identical all-authorized-live-HEAD universe, Boolean
membership, candidate restrictions before ANN limits, original full-distance
ranking, keysets, i64 totals and count scope. Source cards use the same
REPEATABLE READ transaction for page selection and evidence. The selected page
(including lookahead and retained ANN witness IDs) is materialized once in a
transaction-local relation; admission does not rerun candidate retrieval.

Each `ArchiveSourceMatch{view,span,kind,operand,summary}` has its own immutable
view and exact normalized-source UTF8 byte span. Literal evidence selects actual
HEAD messages using PostgreSQL whole-field `lower`/`strpos`, never metadata
fragments or a fabricated first chunk. Whole-field folded character coordinates
are mapped to original scalar boundaries by bounded binary search over lengths
of PostgreSQL-lowercased original prefixes, then converted to UTF8 byte offsets.
Under pinned `pg_unicode_fast` default Unicode lower, U+0130 expands, while
contextual sigma changes character value but not length; prefix lengths remain
strictly monotone. Matches inside an expansion round outward to the original
scalar. SQL checks the enclosing prefix-length inequalities; a violated
projection invariant fails rather than returning an unrelated preview.

Semantic evidence comes only from retained positive-operand ANN candidate IDs,
ordered deterministically by original full distance, operand order, the chunk's
place in its session and chunk ID. The selected chunk is fetched without
retrieval or model calls, after validating
its exact same-session generation/revision pin. At most two representative
matches are returned: when both kinds exist, one literal span and one semantic
span; otherwise up to two literals, or the first real spans from at most two
selected candidate chunks. Representatives are bounded, not exhaustive and not
proof of every Boolean term. Negated operands do not supply evidence (double
negation is positive). Metadata-only, negative-only and metadata-text-only rows
may have no evidence. HEAD and older published matches can coexist without
pretending their revisions are identical. Summary is null for Literal and the
selected stored chunk summary for Semantic.

`ArchiveSearchPolicy` bounds page size to10 and matches per row to2. Mandatory
cumulative source/locator admission is64KiB, including selected page metadata,
lookahead, cursor-anchor materialization, view projections and selected complete
chunk JSON; admission occurs before selected variable-sized fields are fetched
or decoded. Caller source budgets are additionally charged, never enlarged.
Serialized generated `Result.ArchiveSearch` is capped at128KiB. Every statement
(including ACL, cursor resolution, page execution and witnesses) has a thirty-second
deadline or the stricter inherited timeout. Browser source-search requests have a
sixty-second transport deadline, allowing for query embeddings and multiple bounded
source statements; ordinary browser request deadlines are unchanged. These are
per-statement and transport budgets, not a single database transaction deadline. Oversized reads fail `read-budget`,
cancellation fails `deadline`; neither truncates rows, drops required evidence,
changes retrieval membership nor silently falls back. PostgreSQL may inspect
full stored message bodies internally; these limits bound application transfer,
not independent database CPU. Lexical/Hybrid text execution sets transaction-local
`work_mem` to at least16MB (preserving a higher inherited setting) to reduce lossy
trigram bitmap rechecks, without forcing GIN or correlated scans for every query. PostgreSQL applies this budget per plan node,
not per request or process; it is not a global memory cap. Ordinary Archive browse
shares this memory policy, retaining unrestricted materialization and its existing
page-size contract.

Browser dispatch uses explicit fresh `currentBrowser` and the context-read
captured security-epoch delivery checks, before and after the source read.
Source ACL and immutable views are validated in the shared source snapshot;
retired/foreign pins never redirect to HEAD. The existing final-check revocation
race boundary remains unchanged.
