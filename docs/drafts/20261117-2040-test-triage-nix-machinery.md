## 1 Executive summary

**Headline (observed):** in this area the "evidence" layers are not what makes builds slow — each machinery check costs 0.3–1 s — but they are roughly a third of the LOC, they are the largest source of maintenance coupling, and they are tests *of the harness*, not of the product. The wall-clock cost sits in (a) four NixOS VM tests run under QEMU TCG (this host has no `/dev/kvm`): median 197 / 311 / 349 / 477 s, together 1 334 s ≈ half of all serial check time here; (b) `sbt` cold-start + compile repeated in every sbt derivation (the Chronicle "fast backend" check takes ≈60 s for 132 cases that execute in 3.9 s); (c) 33 module evaluations (`nixosSystem`/`evalModules`) in one Chronicle module test plus more in a second (≈21 s + ≈19 s of pure Nix evaluation); (d) serial heavyweight native/browser suites (other agents' areas).

With sharding the longest chain in my area drops from `manure-native` 631–913 s (not changed by my verdicts) / `manure-vm` 477 s to `manure-native` alone.

**Routine-path fact (observed via `nix-store -qR` on the three package drvs):** only `.#chronicle` embeds tests in its dependency closure (`chronicle-fast-backend-validation`, `chronicle-protocol-validation`, `chronicle-fast-validation`, `chronicle-web` with `npm test`). `.#haystack` and `.#manure` contain no test derivations (closures contain only their native/web/client parts; web `doCheck` unit tests aside). None of the unrelated tooling (pi-*, codegraph, tokemon, yolo, crawl4ai, atlassian, rites, ontology, llm-*) is in any of the three closures (grep over `nix-store -qR`: 0 matches each).

### The 10 highest-value actions
1. **Delete the Chronicle receipt chain** (`validation-evidence.py`, `validationEvidence` derivation, wrapper `verify`, `chronicle-validation-policy`, `chronicle-evidence-layout`, orphan `chronicle-validation-fixtures.nix`, `validation-report.py`): −≈540 LOC, keep only the dependency edge to backend/protocol validation. `verify` re-runs `create` on identical inputs (tautology); `validation.json` has no consumer.
2. **Add the missing test, not another receipt:** no Nix check ever *executes* the Chronicle native ELF (it is only SHA-256-hashed by the receipt; `service-unit-graph-vm` uses a synthetic adapter). Add a `chronicle-native` smoke analogous to `haystack-native` (start ELF against owned PG, health, login, one ingest).
3. **Delete the test-of-test-harness group** (unit-graph harness ×2 + `service-unit-graph-controller` phase machinery, `manure-vm-audit/runtime/acceleration`, `test_manure_vm_*`, `service-fixture-*`, `test_manure_release_guards.py`, `manure-installed-shells.py`): ≈3.2 k LOC, ≈0 s but the largest maintenance surface.
4. **Delete frozen/baseline replays:** `manure-acceptance-policy` + `fixtures/manure-posix-acceptance/*.log` (replay logs with 26 contracts; the live probe now prints 32 → fixture already stale) and the 2026-10-31 `agentic-services-legacy.*` extraction baseline (+ snapshot test, + 5 baseline asserts in `agentic-services-hm-eval.nix`).
5. **Shrink the 3 VM tests to one smoke per deployment shape** (NixOS 3-service, HM user-manager, Manure TLS edge): 1 334 s → ≈450 s; TCG is the cost driver, so decide the KVM question (§9) first.
6. **Remove the 5 duplicated XML-inventory/receipt parsers** (`validation-report.py`, `backend-foundation-report.py`, `jvm-inventory-receipt.py`, `native-receipt.py`, `manure-acceptance-report.py`, + the embedded Python in `haystack-native-acceptance.sh`) and `manure-unittests` (composition of receipts): sbt/node exit codes already fail the derivation.
7. **Stop paying sbt cold start per derivation:** merge `backend-foundation` into an existing shared sbt run (losslessJson is its only unique content), DEMOTE `backend-coassembly`, and share one compiled classpath for `chronicle-backend`. ≈25–50 s per derivation saved (estimate from 60 s vs 3.9 s).
8. **Cut module-test evaluation cost:** `chronicle-modules`/`chronicle-models` use 33 `nixosSystem`/`evalModules` evaluations (21 s + 19 s measured). Switch to stubbed `evalModules` (the pattern already used in `haystack-nixos-eval`).
9. **Collapse ≥10 copies of the same invariant** ("migration unit `Requires` its database unit") into `shared-services-modules.nix`; move the 314-line inline `haystack-*` module tests out of `flake.nix`; delete three tautological `dev-llm-*` import checks (flake.nix:66-76).
10. **Parallelise by sharding derivations, not by tuning runners:** each derivation already owns its PostgreSQL cluster on an ephemeral port, so splitting `haystack-native`/`haystack-browser`/`manure-native` by test file or by atomic/markup/browser into N derivations is safe; inside one derivation use per-test databases from a template and drop the global provisioning `flock` (§5).

## 2 Method and measurement conditions

* Host: `bigvm0`, 128 cores, load average 125–155 throughout (shared with ≈8 agents); `uptime` recorded in `eval-times.meta`, `rerun.meta`. `nix config show`: `max-jobs = 8`, `cores = 16`, `system-features = benchmark big-parallel nixos-test uid-range` (no `kvm`); `/dev/kvm` absent (observed `ls`).
* **Read depth**: read in full or nearly so — Chronicle validation chain, backend-foundation/receipt scripts, manure-unittests/native/portable-root/backend/config, manure-acceptance/direct-jni/posix-acceptance, haystack-native/browser/proxy + acceptance script, unit-graph VM/controller/harness, shared-postgres/provider tests, chronicle-modules/models, shared-services/shared-postgres modules, service-accounts (first ~120 lines), source-filter tests. Skimmed (head + assertion/grep profile only): `manure-nixos-eval`, `manure-hm-eval`, `agentic-services-hm-eval` (tail), `service-cli-hm`, `chronicle-hm-server`, `oci-images`, `manure-vm.nix` body and `manure-vm-audit.py`/`manure-vm-runtime.py` internals, `manure-client.nix` body. Verdicts for skimmed files rest on structure, references and cost, not on a line-by-line review.
* **Read**: every file in scope was opened or grep-profiled; external-reference checks were done with `grep -rn` over `*.nix *.sh *.py *.md *.json *.mjs *.ts` (qualifier: "unreferenced" means no hit outside the file itself and `docs/drafts`).
* **Historical durations** (superscript ʰ in the table): taken from `reports/build-profile/hist-durations.txt` (build-profile agent; duration = birth→mtime of `/nix/var/log/nix/drvs/*.bz2`, median over n builds; includes contention, so max values are unreliable — e.g. `chronicle-fast-backend-validation` max 3 274 s vs median 60 s). I did not re-derive these; I spot-checked drv names against `checks-drv-f153d1ae.json`.
* **Measured** (ᵐ): `nix build -L --rebuild --no-link .#checks.x86_64-linux.<name>` wall time including Nix start-up/eval (≈0.2–1 s floor), per check, 3 in parallel, load ≈140–150 (`rerun.tsv`). Fast python/eval checks only; I did not run VM, native or browser suites (owned by other agents; heavy). One accidental start of `manure-unittests` began building the portable-root VM (248 derivations) and was interrupted by me after ≈2 min (guest systemd reached multi-user at ≈85 s TCG, observed in `logs/manure-unittests.log`); nothing of mine remains running.
* **Eval-only** (ᵉ): `nix eval --no-eval-cache --raw .#checks.x86_64-linux.<name>.drvPath`, 6 in parallel (`eval-times.tsv`, sum 190 s for 61 checks). For eval-only checks this *is* the cost (build body is `touch $out`).
* Derivation-level non-determinism observed: `manure-direct-jni` and `manure-posix-acceptance` fail `nix build --rebuild` ("may not be deterministic", `logs/*.rebuild`): their outputs embed logs/timestamps, so they can never be bit-for-bit checked.
* Taxonomy tags use the `constructive-test-taxonomy` axes (Behavioral/Active default omitted; Blackbox/Effectual/Whitebox × Atomic/Group/Good-communication); "(of machinery)" marks tests whose subject is test tooling rather than the product. Only assertions about product contracts are credited as "KEEP".
* Not done: no per-case timing inside the VM tests, no mutation testing of the proposed deletions (a canary-mutation list is in §7), no run of the other agents' suites.

### 4.1 The Chronicle receipt/evidence chain (DELETE, rows 1-6)

## 5 Parallelism blockers and plan

**Observed blockers**
| Blocker | Evidence | Scope |
|---|---|---|
| `max-jobs = 8`, `cores = 16` on a 128-core host | `nix config show` | across derivations |
| One PG cluster per derivation, tests serialised | `haystack-native.nix:38` (`--test-concurrency=1`), `haystack-native-acceptance.sh:50`, `build.sbt:88,210` (`parallelExecution := false`) | inside derivation |
| Provisioning serialised by a global `flock`, HBA rewritten + `pg_ctl reload` per database | `provision-owned-database.py:31,53` | inside derivation |
| Chained sequential commands (`atomic && markup && browser`) in one derivation | `haystack-native-acceptance.sh:37-56` | inside derivation |
| sbt cold start + compile repeated per derivation | 60 s vs 3.9 s, `backend-foundation` 24 s, … | across derivations |
| VMs: 1–2 vCPUs, TCG, ≈85 s guest boot | `manure-vm.nix` (no `virtualisation.cores`: framework default, one-vCPU budget per its header notes), `service-unit-graph-vm.nix:37` (`cores=2`); guest at multi-user after ≈85 s (`logs/manure-unittests.log`) | per VM |
| Aggregators serialise heavy checks behind one name | `manure-unittests` (248 derivations) | graph |

**Not a blocker (inference, not observed):** fixed ports across derivations — Nix sandbox builds run with a private network namespace, and every fixture binds port 0 (`with-owned-postgres.py:24`, `shared-postgres-test.py:39`); I did not run two instances side by side.

**Cheapest route (ordered)**
1. Raise `max-jobs` for the build host (config only; 128 cores vs 8 jobs).
2. Shard derivations: `haystack-native` by test file, `haystack-browser` into atomic/markup/browser, `manure-native` by target-suite group; each derivation still owns its cluster and port.
3. Inside a derivation: build one template database (schema + pgvector) and `CREATE DATABASE … TEMPLATE`; remove the per-DB HBA rewrite by a single wildcard rule for the owned cluster; then raise `--test-concurrency` to N cores.
4. One shared compiled-classes derivation consumed by all sbt checks (needs the build-profile agent's graph analysis).
5. VMs: only after the KVM decision; if TCG stays, run one VM per shape in parallel (they are independent derivations) and give TCG guests more vCPUs.
