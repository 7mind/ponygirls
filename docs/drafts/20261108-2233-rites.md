## User requirements

- Name: **Rites**.
- Maintain local copies of explicitly configured GitHub/GitLab repositories.
- Support GitHub tokens and GitLab tokens/OAuth access tokens.
- Each repository has named rites: schedule, repository-relative Markdown prompt,
  and configured model.
- On schedule fetch updates, execute the prompt with Pi embedded as a library,
  and create a PR/MR if the resulting repository content differs.
- New changes supersede the previous unmerged proposal for the same rite.
- Stack: Baboon, Scala, distage, BIO, Izumi, logstage, TypeScript, native-image.
- Browser-managed repository/rite configuration and credentials with multi-user
  authorization (Q39, answered revision 2).
- Use privately configured models for live acceptance; do not record local model
  choices, endpoints, account information, or credentials in this repository.

## Confirmed design decisions

### Q39: answered — browser-managed multi-user service

User selected browser-managed repository/rite configuration and credentials with
multi-user authorization. PostgreSQL, not declarative repository configuration,
is the authority for mutable product configuration. Only infrastructure settings,
bootstrap identity configuration and runtime key paths remain operator-managed.

### Q41: answered — static accounts and repository grants

Use the proposed operator-provisioned password accounts and repository-scoped
owner/editor/viewer grants for this release, with Chronicle-style static account
configuration. No public signup or credential retrieval. Credentials are
write-only, user-owned and explicitly bound to repositories.

### Q40: answered — Linux bubblewrap with regular networking

Use bubblewrap for filesystem/process isolation and ordinary outbound networking.
Configured repositories and model endpoints are trusted recipients of their data.
This is **not** an egress or exfiltration boundary. Do not inherit host secrets,
other repositories or service state merely because networking is unrestricted.

## Proposed behavior

These are proposed implementation policies, not additional user approvals.

### Identity and scheduling

A repository has a stable operator-selected ID and one fixed forge identity.
A rite has a stable ID scoped to that repository. Replacement never crosses
this `(repository ID, rite ID)` boundary. A run has a UUID, configuration revision,
scheduled UTC instant, resolved base commit, and prompt digest. Renaming IDs does
not adopt or close existing remote proposals implicitly.

Use five-field cron in UTC for the first release. Reject unsupported syntax;
do not reinterpret invalid schedules. Deduplicate by rite and due instant.
Coalesce missed ticks after downtime into at most one catch-up per rite rather
than replaying an unbounded backlog. Persist the schedule cursor and admission
atomically. A manual trigger has its own idempotency key. Never overlap runs of
the same rite; initially serialize repository Git maintenance as well. Global
concurrency and queue lengths have explicit finite bounds.

### Repository preparation

The coordinator alone fetches and maintains the repository mirror. Each run
gets a fresh workspace from the current configured base branch; it does not
continue the preceding proposal branch. Record the resolved base revision
before agent execution. Read the exact Markdown blob from that revision, reject
absolute/traversal paths, symlinks, non-regular files, invalid UTF-8 and oversized
prompts. Do not execute Git hooks or recurse into submodules automatically.

Agent-controlled Git metadata is not a publication authority. After execution,
export validated content into a coordinator-owned clean publication checkout.
Do not trust agent-created commits, remotes, hooks, index flags or git config.
Compute a tree delta including tracked modifications, deletions, modes and new
non-ignored files; validate submodule/symlink and size policies explicitly.
A success claim from the model is not evidence of a diff or passing tests.
Model error, refusal without completion, cancellation, timeout or sandbox
failure must not publish partial changes.

### Pi worker

The Scala coordinator remains a native executable. The TypeScript worker embeds
the pinned Pi SDK; it is not a shell invocation of the interactive Pi CLI.
The worker uses a fresh session, explicit resource loader, explicit tools,
in-memory settings, and operator-selected model configuration. It must not
inherit personal extensions, project executable extensions, MCP servers,
credential discovery, or session history. Repository instruction files, if
supported, are data under an explicit policy, not executable configuration.

Worker input/output uses Baboon-generated Scala and TypeScript DTOs. The
coordinator bounds framing, bytes, events and runtime. The supervisor owns a
monotonic deadline and kills the entire worker process group on expiry; SDK
abort alone cannot establish that background children exited. Exactly one
terminal result is accepted and verified against the worker exit status.
Diagnostic output must not be mistaken for protocol messages.

Model credentials are runtime-only and scoped to the worker. Forge credentials,
database passwords, control-plane tokens, other repositories and coordinator
state must not be visible to repository code. Filesystem confinement must be
verified with negative controls. Networked agent code can still disclose
repository content to permitted destinations; document this residual risk.

### Proposal publication and replacement

1. Only a successful run with an observed nonempty content delta can publish.
2. Commit the delta on a unique Rites-owned branch derived from the base commit.
   Never force-push a shared branch or push the configured base branch.
3. Revalidate current rite authority and base-branch policy before publication.
4. Persist the intended branch/run identity before pushing or creating a proposal.
5. Open a new PR/MR and independently verify forge identity, source/target,
   ownership marker and current open state.
6. Only then close older still-open Rites-owned proposals for that same rite.
   Re-read each immediately before closing; merged or human-owned proposals are
   never closed. Preserve predecessor branches in the first release.
7. A failure to close a predecessor is visible `supersession pending`, not a
   fully successful replacement. Retry closure separately, not the agent run.

No-change and failed runs leave the old proposal open. Equivalent changes to an
already-open proposal should be detected and reported without needless churn.
The exact comparison must preserve the base and resulting tree identities.

GitHub/GitLab and PostgreSQL do not share an atomic transaction. A crash after
remote creation but before local acknowledgement leaves an uncertain attempt;
reconcile by durable run marker and branch before retrying. Never interpret a
timeout as proof that no remote write happened. If reconciliation cannot prove
identity/ownership, stop publication and expose the uncertainty. Temporary
overlap of two proposals is preferable to closing the only valid one before
replacement creation succeeds.

## Proposed architecture

```text
browser UI + authenticated API / operator infrastructure settings
                  |
       native Scala coordinator
       distage graph / BIO services / logstage
          |         |           |
     PostgreSQL   Git cache   forge HTTP adapters
          |                     GitHub / GitLab
       scheduler / durable publication reconciliation
          |
    isolated per-run process
    TypeScript + pinned Pi SDK + fresh workspace
```

Browser-managed secrets are encrypted at rest with authenticated encryption and
an operator-provided runtime master-key file outside the database and Nix store.
Secret APIs return metadata, never plaintext values. Bind ciphertext to credential
identity/owner using associated data; use fresh nonces and explicit key IDs.
Key loss and rotation require a documented operator recovery procedure; a backup
of ciphertext without the matching key is not a recoverable credential backup.
Never send stored forge secrets or ciphertext to the agent/model. Avoid plaintext
secrets in request/exception logs, traces and database audit events.

Repository configuration, grants, credential bindings and rites carry revisions.
A queued/running job captures the relevant revisions and must revalidate current
authority before publication. Removing an account, grant, repository or credential
must block undispatched publication. A remote request already dispatched cannot
be retroactively revoked; retain its uncertainty and reconcile observed effects.
Keep configuration management independent of worker-controlled files.

Keep domain logic independent of concrete transports:

- `RunRepository`: admission, schedule cursors, attempts, terminal outcomes,
  publication intents, observed remote receipts and recovery state.
- `RepositoryWorkspace`: fetch, immutable prompt read, isolated snapshot,
  validated output export and coordinator-owned diff/commit.
- `AgentRunner`: bounded subprocess protocol, cancellation and exit observation.
- `Forge`: observe/create/close proposals with repository and ownership identity.
- `Clock` / schedule evaluator: deterministic due-time calculation.

Use BIO for effect-polymorphic application interfaces, not merely a dependency
name. Select a supported concrete bifunctor runtime and bridge existing
cats-effect/http4s/JDBC facilities at adapters. Keep one canonical compiled
Baboon runtime. Use distage auto-wiring and lifecycle resources; validate the
production graph without classpath scanning in native-image. This does not
justify migrating existing services from their current effect runtime.

GitLab OAuth access-token support does not imply an interactive OAuth login or
refresh-token broker. Validate issuer/instance and expiry; expired credentials
produce a visible authentication failure until operator rotation unless a
separate refresh contract is explicitly chosen.

## Implementation sequence and observable acceptance

1. **Plan and protocol foundation** (independent of Q39/Q40).
   Define worker DTOs and bounded/versioned boundary validation. Verify Baboon generation,
   Scala/TypeScript codec behavior, malformed/versioned input rejection and
   replacement policy with deterministic tests. No runnable service claim.
2. **Durable coordinator and scheduling** (after control-surface decision).
   Add Rites projects to the shared build, migrations, config validation, BIO
   application services and distage graph. Run one repository/admission contract
   against dummy and owned PostgreSQL; test concurrent admission, restart and
   catch-up with a deterministic clock.
3. **Git and sandboxed SDK execution** (after isolation decision).
   Use disposable local bare repos and synthetic prompts. Verify fetch, base
   identity, no-change, deletion/new-file/mode changes, prompt safety, model
   errors, timeout, child-process termination and confinement negative controls.
4. **Forge adapters and crash recovery**.
   Use local HTTP fixture servers for GitHub and GitLab: auth headers, escaped
   project identifiers, pagination, redirects, rate limits, timeouts, uncertain
   create outcomes, recovery, author/branch ownership and same-rite replacement.
   Remote live mutations require separately authorized disposable repositories.
5. **Control surface, packaging and native acceptance**.
   Build the chosen UI/API, native coordinator and pinned SDK worker; verify
   Nix module policy, artifact provenance and native-runtime behavior, not just
   JVM tests or ELF existence. Do not enable a deployment as a side effect.
6. **Controlled live-model acceptance**.
   Use synthetic repository content and an external private configuration.
   Verify an actual SDK-driven edit and no-change/error controls. Deterministic
   scripted models verify workflow, not agentic/semantic quality. Keep raw live
   traces and local model selection outside tracked source and build inputs.

## Validation evidence to preserve

Record source identity and exact commands, discovered suite/case counts,
failures/errors/skips, native artifact binding, live versus scripted providers,
and remote fixture versus real-forge coverage. A fast Nix build is not full
acceptance. Changes to shared packaging/build inputs require their applicable
policy checks and Chronicle's complete release suites under `AGENTS.md`.
