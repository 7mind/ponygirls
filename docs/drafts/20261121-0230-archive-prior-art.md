# Managing old coding-agent tool output: what the prior art supports, and three tests in Pi

**Recommendation: keep the shipped pointer + literal `find`, and keep archiving off by default.** Of the new ideas, the most promising is a small verbatim preview for result types with informative headings or footers, **without changing FIFO selection**. It avoided some extra retrievals in both runs, but was not consistently faster or cheaper. Selecting later cold entries to preserve the prefix produced a measurable cache benefit on one of three model routes. A separate replay found that deferring marginal edits helps or hurts depending on cache lifetime and the remaining workload. We retained the prototype for research; the report and reproduction tools do not change the shipped runtime.

**Evidence:** more than 20 directly cited papers/preprints/reports, six inspected codebases, 24 sampled public coding traces, 360 controlled offline replay rows, and two live rounds of 30 sessions. The literature and source comparisons follow the live findings below. The accompanying numeric data pack contains per-session metrics, all replay cells and the public trace-shape data. The local retained copy is `debug/20261121-0230-archive-prior-art/publish-data/`. Percentages from papers, synthetic cache equivalents, and costs measured on live requests are kept separate.

**Test 1 — what to leave behind.** At FIFO placement, a preview cut the calls to `context_recall` on the edge-addressable question from **19 → 10** in round 1 and **18 → 12** in round 2 (the edge stage completed in all six blocks both times). On the complete five-way blocks, total session tokens fell **16.9% / 6.3%** versus FIFO pointers with no baseline-correct answer lost. But wall time changed **−16.8% / +15.9%**, and SDK catalog-price estimates changed **−11.8% / +4.2%**. The preview is not free: when the needed record is in the middle, it can cost another turn or make the visible stale alternative look convincing. At late placement edge-probe recall calls were 18 → 18 / 18 → 12; end-to-end token and time effects were likewise different. Do not credit the combined policy with two independent wins. This is evidence to test previews on *real output types with useful edges*, not to keep 320 characters from every tool forever.

**Test 2 — where the prefix breaks.** On the first unrelated follow-up, the rendered message-array prefix common to WARM and the control grew from **625 → 25,059 bytes** on the Token Factory wire format and **1,733 → 26,079** on Codex when moving from oldest to latest eligible. That increase occurred with both representations in both rounds, before any recall. But a byte comparison does not tell us whether a provider reused KV state. RAW demonstrates that all three routes *could* reuse this history. DeepSeek sometimes reused an appreciable prefix after editing; Kimi and Sol reported no such hit here. These data do not identify which internal cause—eligible breakpoints, routing, cache implementation or retention—produced a miss. Later-first is also a semantic choice: which two observations remain raw changes. In the repeat DeepSeek gained one edge answer but lost one middle answer with late pointer vs stock. Do not sell this as a provider-independent cost optimization.

**Failure analysis.** The handbook edge task joins a published artifact path with a final checker code; its middle task computes the latest *released* mount and landing page despite plausible earlier/proposed records at the ends. The rollup task similarly joins an exact decoder profile and quarantine path, then derives a two-field bucket configuration whose behavior is checked on boundary ticks. Both older and later candidate pairs contain one required observation for each task. One initial DeepSeek late-edge middle answer failed to parse as the requested JSON after four successful literal finds; the full originals remained accessible. On the repeat, DeepSeek handbook late-pointer output failed to parse, while late-edges got the base right but **the landing filename wrong**. DeepSeek also missed the rollup decoder profile while getting the quarantine path right in **both RAW and FIFO-pointer**. These are format failures and/or answer errors, not evidence of corrupt storage. We don't know which stale value the model chose from a field-level boolean alone. There was no retrieval-coverage failure in the completed post-run exact-read audits.

**Next decision.** Do not build a vector store, another summarizer, or lower the normal trigger on this evidence. The cheapest path when these histories fit was to leave them alone. Under genuine sustained pressure, first measure the *opportunity*: how often is there a real choice of cold targets, which tools generate those targets, how many turns remain, and whether there is an actual cache hit to lose. A useful next controlled test is a tool-specific, verbatim status/locator preview on full repairs with execution-based grading and natural pressure, against today's stock archive. Require it to save whole-task work across repeated runs, not merely to make a first retrieval smaller. Any timing gate should expose a hard headroom limit and fall back to normal native compaction if no safe release is possible. More search sophistication is a different question: first exhibit a failed lookup that literal search cannot express.

## What the literature actually distinguishes

Three properties are often called “memory,” but they are not interchangeable: **the bytes still exist**, **the agent can locate the right bytes**, and **the next decision is correct**. A fourth question is whether fetching those bytes was cheaper than having left them in the prompt. We looked for evidence on all four. Below, numbers in the literature review are *reported by the authors*, not replications. Our own measurements are identified separately.

### 1. The closest prior art is addressable storage, not a bigger context window

- [Dang et al., *Addressable Recall Compaction* (ARC), algorithm, results and Apps. A–B](https://arxiv.org/html/2607.25066v1). A stored observation has a stable ID. The rendered citation contains a head preview, tail preview, metadata and a recall hint; recent turns stay raw. **This is direct prior art for our preview**, not just an analogy to summaries. The published comparison tests the *whole* ARC protocol—not head/tail versus the same address without a preview. It reports 99.40% versus 88.12% on a forced-compaction random-needle task, but 29.97% versus 28.25% on LongBench-v2 Hard, averaged across Qwen3-8B/32B. Serving time is a hardware/roofline estimate, not a hosted bill. Even the spec deserves care: the formal chunked-recovery guarantee assumes exact pages, whereas App. B describes a head/tail-limited recall for an oversized result in the evaluated configuration. A durable original is not enough if its middle cannot be requested. We retain our existing arbitrary-offset, hash-checked `read` and literal `find` in every archive arm.
- [Yang, Shi & Zhao, *Forget Freely, Grep Later*, §§3–5](https://arxiv.org/html/2611.25123v1). GrepMem adds a lossless append-only transcript and index-free regex lookup to a summarise-and-resume baseline. Five strategies were separately RL-trained on Qwen3.5-9B (32,768-token window, 4,000 training episodes); the authors report 95–97% on their ContextBench setting versus at most 21% for lossy baselines. They also evaluate before training. This is close independent support for trying lexical access before building embeddings, **not** that a new regex operator delivers that gain in Pi: full transcripts, training and task distributions differ. Our `find` is narrower by design—literal search in manifested fields of the current branch, not every user message.
- [Packer et al., *MemGPT*, §2](https://arxiv.org/abs/2310.08560). A bounded working set, a FIFO message queue, an external recall store and a model-mediated paging interface were already explicit. The evaluations were multi-session chat and document analysis, not code repair with a hosted prefix cache. [Ehrlich & Blackman, *LCM*, §§3–4](https://arxiv.org/html/2605.04050v1) goes the other direction on control: the engine builds a summary DAG with lossless pointers and supplies parallel map operators. Volt averaged 74.8 vs 70.3 for Claude Code on OOLONG-synth `trec_coarse`, with the same primary Opus and access to Haiku. That is a system-level aggregation result: it does not isolate the DAG, establish repair quality, or demonstrate a need for a DAG when our flat catalogue suffices.
- [Zhang, Kraska & Khattab, *Recursive Language Models*, observations 1–3 and limitations](https://arxiv.org/abs/2512.24601). Putting large input in an external environment lets the model inspect and partition it; recursive subcalls helped on information-dense aggregation, but the no-subcall variant won on one CodeQA configuration. This is a different workload from “find the literal build receipt.” Do not buy another inference graph just to locate a string. [LongMemEval, §3.2](https://arxiv.org/html/2410.10813v2) supplies a better task taxonomy than one needle: extraction, aggregation, updates, temporal reasoning and abstention. It is a 500-question chat-memory benchmark, not coding-agent cost evidence. We borrow the idea of a superseding record, not its score.

### 3. Cache disruption is a client concern; KV eviction is not a client power

- [Cim, Topcu & Kandemir, *Break Later or Never*, §§IV, VIII, X](https://doi.org/10.6084/m9.figshare.34791231.v1). Distinguish the deployable **batched prompt masking** experiment from **ObsDrop**, their modified SGLang/vLLM engine. In their two-model/two-SWE-benchmark characterization untreated traffic reused 98–99% of the prefix. Batched masking maintained 95–98% reuse, with *up to* 18% lower serving cost and 21% lower completion time. The 2.45–2.85× FlashInfer throughput result is for the **server-side** method under concurrency, not a benefit one can get by reordering client messages. Our “late” policy chooses later cold targets; it does not claim to implement ObsDrop or to preserve all prefix KV.
- [Hao et al., *Self-GC*, “Recoverability and Cache-Aware Commit” and Tables 1–2](https://arxiv.org/html/2607.00692v1). Separate planning, rehearsal and commit. They estimate future savings minus prefix-break and planner overhead before publishing an edit. Their 33-session hard-set “no impact” (84.85%) is a *future-aware judge rating*; the online 10–15% daytime average input reduction is an account-name split covering multiple mechanisms, **not a randomized quality or whole-bill audit**. A useful portable ingredient is delaying a marginal edit, without adding their side-model planner. A learned pruning fraction from their deployment is not a universal default.
- [Xu et al., *TokenPilot*, §4.3 Table 3](https://arxiv.org/html/2606.17016v1): stabilizing the ingestion prefix cut continuous PinchBench cost $7.24 → $4.22; adding lifecycle-aware eviction cut it to $2.79. The stages combine several actions; this is neither an isolated target-order study nor a blanket 61–87% projection for Pi. [Nguyen et al., *CliffCompaction*, §2 and Table 8](https://arxiv.org/abs/2609.26779) provides a useful contrary case: only truncate/drop original context, never re-summarize a summary. On mini-SWE/Verified Kimi K2.6 had practically unchanged reported cost at 32k and slightly *higher* cost at 8k; GLM benefited substantially. No historical read-back is guaranteed by this algorithm. Model, workload, cache and threshold interact.
- [Kumar & Pandey, *TurnCost*, §§3, 5.1–5.6](https://arxiv.org/abs/2610.15093): replay of 600 published trajectories, two scaffolds/two models; median observations 118–286 tokens. The reported 98.6% cache-hit share is from a near-ideal prefix simulation. Turns explained more log-cost variance than mean observation size (84% vs 4%); that association does not prove deleting a turn is safe. This motivated a separate check of how exceptional our four large inputs are.
- [Anthropic’s context-editing API, “Context editing and prompt caching”](https://platform.claude.com/docs/en/build-with-claude/context-editing) explicitly says clearing can invalidate a prefix and offers `clear_at_least`, `trigger`, `keep`, exclusions. That is documented behavior, not a benchmark for the other providers. [OpenAI prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching) requires an exact **rendered** prefix, eligible boundaries, routing and lifetime; sessions do not guarantee hits. Some newer Responses models append top-level `instructions` after `input`. Our check therefore namespaces the **first user content**, rather than assuming a system string isolates a session. [Fu et al., *Cache Engineering for Agents*, §§3–4](https://arxiv.org/abs/2610.28577) requires a serving API carrying drop/reposition history and an AKV engine. Neither Pi's context hook nor a client longest-common-prefix count grants that capability.

### 4. Who writes memory, and under what incentive?

[billion-context, pinned implementation and preprint v0.2, §§7–8](https://github.com/ranxianglei/billion-context/blob/6a641f378537e06e7430ec90c9abf035ffa12377/paper/model-driven-incremental-hierarchical-compression-training-free-multi-generational-context-management-for-long-lived-coding-agents.md) separates the model's task-conditioned choice of a range from retaining exact sources. In its single quiescent control, instructions + ID tags without a compression reproduced 62% fewer re-fetches versus the 63% headline. Its 28.6B figure is a fitted cumulative-input simulation including cache re-reads. [Busch et al., *CTXAgent*, §3.1, Table 1 and limitations](https://arxiv.org/abs/2610.34425) found frontier models can manage context over 35–212-turn workloads using `compact_context`/`curate_context`, **plus** explicit guidance and a periodic review hint. That is a different incentive from an optional tool advertised only in a schema. Neither study gives us a free second summarizer or proves notes are used.

Our earlier experiments matter to selection. In six matched final fold pairs, a side-model digest reduced total tokens 8.9% but uncached input rose and one exact lookup regressed. In two rounds of literal `find`, complete recall text fell 70–80% at unchanged answer accuracy, but uncached input moved in opposite directions. In the subsequent note trial **zero of six** offered agents tried to save a note, and all twelve native checkpoints named the original choice. The next experiment should not repackage those as new findings. We focus instead on *where a deterministic edit first breaks the prefix*, *what literal text is worth carrying without an extra model call*, and *whether the edit should be committed yet*.

**Evaluation precedents, not efficacy claims.** [Zhang et al., “Masking Stale Observations Helps Search Agents—Until It Doesn’t”](https://arxiv.org/abs/2606.00408) found gains varied by retriever and model and could vanish for a strong starting system; web search is not coding. [Liu et al., *Lost in the Middle*](https://arxiv.org/abs/2307.03172) varies the position of relevant documents/keys; it does **not** establish that the middle of a single log is disposable. [Factory's published vendor evaluation](https://factory.ai/news/evaluating-compression) scores recall/artifact/decision/continuation probes over 36,611 **messages**, using a judge; useful test types, not blinded user productivity or end-to-end billing evidence. We deliberately use exact independent scoring and record which observations were actually edited.

**Selection method and limits.** We searched scholarly titles/abstracts for observation masking, prompt/KV caching, exact addressable recall, recursive context, trained pruning, and agent continuation; followed references and checked the cited tables/sections against primary texts. We separately inspected official API docs and revision-pinned implementations; [the engineering appendix](20261121-0230-comparative-harnesses.md) includes line links to six codebases and seven revisions. In particular, Codex and mini-SWE-agent clip at first delivery, SWE-agent's optional history processor batches omission by polling interval, and old vs current OpenCode place pruning/summary work at different lifecycle boundaries. None of those facts by itself is an efficacy test. We used preprint revisions available by the date above and older version-pinned snapshots where noted; search engine duplicates and publisher mirrors do not count as replication. This is a mechanism-led, English-language selection, not an exhaustive priority claim. We excluded methods requiring training, arbitrary external execution or provider KV access from the *implementation pilot*, not from the literature review.

## A check on real workload shape

Before scoring policies, we sampled **24 public mini-SWE-agent v1.0 / GPT-4.1 trajectories**: eight each from SymPy, Matplotlib and Sphinx in the [pinned SWE-bench submission](https://github.com/SWE-bench/experiments/blob/40f164d5b8f1d249bf95a6df8b74b577fd8e519d/evaluation/verified/20250726_mini-v1.0.0_gpt-4.1-2025-04-14/metadata.yaml). Selection took the eight smallest salted SHA-256 path hashes per project without consulting outcomes. There were **573 already-rendered observation texts** (user-role replies immediately following assistant actions; not original untruncated stdout). Nearest-rank median was **456 UTF-16 units**, p95 **3,249**, maximum **56,049**. Only **22/573 (3.8%)** reached 4,096 units, but these accounted for **194,585/604,111 (32.2%)** of the observation characters. Thirteen sampled traces had any such result; **only one observation in the sample reached 12,000**, and none of the 24 would have had four cold results that large at the end. A static char/4 estimate (no provider overhead) put none above 70% of even 65,536 at the end. This is a small, stratified sample of one prior harness—not our production distribution. It both justifies caring about outliers and rules out treating the live stress fixture as typical. We did not execute these repositories or send the public trajectories to model providers. Reproduce with `python3 scripts/experiments/archive-public-shape.py NEW_DIR --frozen`; the repository includes the 24 public object keys and SHA-256 hashes. The unsuffixed invocation also rechecks the live sampling frame. Fetching the frozen bytes twice produced the same metrics JSON (`ad749a24…c412`). No raw trajectory text was retained in the aggregate or sent to providers.

## Scope and protocol (set before live results)

Design-oriented evidence review as of **21 November 2026**, not a systematic review or a meta-analysis. The question is what a client extension can do to keep tool-heavy sessions usable and economical **without losing a route back to the exact historical observation**. We distinguish tool presentation at first delivery, reversible edits to older messages, retrieval, model-generated summaries, and serving-side KV operations. They have different costs and failure modes. An output file read *today* is not necessarily the output observed earlier.

**Live factorial.** Two independent factors: (1) remove the oldest eligible cold observations first (stock FIFO), or the **latest still eligible** first to retain a longer exact prefix; (2) render a pointer alone, or keep a bounded verbatim head and tail (*edges*) around an explicit middle omission plus the same recovery route. Both use the same Pi archive eligibility, original message IDs/digests, protected recent suffix, and literal find/read/list tools. No model or index is added. The fifth arm, **raw**, retains the originals with the same declared recall tool but no archive edits. No branch represents an installation or reproduction of another agent harness.

For each of two fresh benign software-maintenance scenarios and each of three prior model routes (Token Factory DeepSeek V4.1 Flash and Kimi K3.1 Pro; Codex GPT-6.2 Sol), run all five arms. Four 12,000-character old observations permit a matched single release: exactly two older or two later cold results, equal raw sizes; net savings include the preview. First send one genuine acknowledgement with the original history; commit one batch at that boundary, then keep the policy quiet. The first post-edit question needs **none** of the old evidence (cache-isolation control), then ask an edge-addressable question and a middle/correction question in the same session. The fixtures rotate where the evidence lives. A bounded exact scorer is independent of the runtime, not an LLM judge. Results naturally may carry forward. Force the single boundary without faking the answering model's monetary usage or reducing its capacity. Assign each session an opaque leading cache namespace; balance the run order. No private source, real user sessions or unrelated tools in model inputs. Protocol failures and incomplete generations remain visible, not successes.

**Realized treatment.** Before WARM all arms enable the same production `context_recall` declaration and park watermarks at 100% / 99%. On WARM completion, edited arms set a one-boundary pulse from actual provider-accounted usage on the unchanged model capacity: trigger just below measured usage, release toward 5,000 fewer Pi-estimated tokens. The existing native selector receives the true history, six-turn and 16,000-token protection, 4,096 minimum batch and 16-target cap. The runner parks the thresholds again before settlement; it never turns archiving off to undo an edit. RAW stays parked. Per edited session the stock stubs released 5,846 estimated tokens, previews 5,648 (including labels and omission notices); these are Pi estimates, not provider token differences. Exact full bodies, projected slot, index, digest and untouched suffix were checked; unarchived originals cannot be retrieved through the archive tool. Host-only exact read/find verification ran **after the timed prompts**, not as hidden free agent help.

All model requests are real, using synthetic inputs only; provider limits, usage splits and operation errors were recorded per POST. The 32-hex-character nonce was stable within the session and randomized between sessions before the first large common observation on both wire formats; we verified identical warm request contents after normalizing that nonce. Relative positions were counterbalanced across the six model/scenario blocks. `control` uses no historical value and the **first** POST is measured before a possible recall changes context. Later probes can see prior results. A second full run was planned during the first, before overall five-way results were available, with new namespaces for all cells and no prompt, key, task, policy or model changes. This measures repeatability, not generalization to fresh tasks. When choosing later candidates, native manifests are emitted newest-first: subsequent lists and broad `find` results can therefore differ in order as well as in which evidence is archived. Whole-session behavioral effects cannot be assigned to cache lookup alone. Equal source character lengths also need not be equal token lengths under a given model tokenizer.

**Primary contrasts:** placement = late-stub vs fifo-stub and late-edges vs fifo-edges; representation = fifo-edges vs fifo-stub and late-edges vs late-stub. Report case-level reversals and interactions rather than attributing the combined arm to both. For placement, test structural unchanged prefix and observed first post-edit uncached/cache-read tokens, then end-to-end. For previews, test whether the edge probe avoids recall and whether the middle probe is harmed or needs more work. Count exact typed answers, normalized total/fresh/cache/output tokens, actual calls and summed session time. Cache accounting counts what the provider reported, not an estimate of residency or an invoice. RAW distinguishes a better intervention from needing to intervene at all. This small one-sample-per-cell study can motivate further work, not a production-default change. A favorable exploratory signal needs no baseline-correct answer lost in the matched slice, a material reduction in the targeted measure, and no compensating growth in full-session work that invalidates the proposed use. No tuning of the corpus, scorer or policy on scored results.

**Separate replay:** exercise a possible decision about *when* to edit over controlled synthetic growing trajectories using the public planner. Compare with existing 70/50 hysteresis and RAW under multiple horizon/cache/pressure assumptions, including insufficient eligible data. Express the break-even explicitly. This is a counterfactual cache/pressure study, not a behavioral benchmark, provider latency measurement or proof of savings in production.

## When should an edit be deferred? Offline sensitivity, not a provider experiment

[`archive-cache-replay.mjs`](../../scripts/experiments/archive-cache-replay.mjs) takes the unmodified stock planner and its actual proposed native edits. At each boundary let **S** be the estimated input tokens saved by publishing them and **D** the number formerly in the reusable prefix that would no longer be reusable (including removed tokens). With fresh input priced at 1, cached input at *r*, and *H* expected future requests, the edit's rough advantage for an otherwise stable hot prompt is **S × [1 + (H−1)r] − (1−r)D**. This follows by charging the first request for its fresh suffix and subsequent saved tokens at the hit rate. It assumes no extra retrieval calls, future edits or expiration in that forecast; the replay *then* tests these assumptions rather than treating the formula as truth. The gate used H=4, r=0.10, committed regardless at 90% pressure or when caching was known unavailable, and never weakened stock eligibility. The estimate uses complete matching message prefixes, not vendor tokenization. A deterministic oracle forced genuine 512-character historical reads in the revisit cases; no real agent or server answered.

Five fixtures (low, dense, partial release, streaming growth, insufficient eligible), 64k/128k-class windows, four revisit positions, warm/expiring/off caches, 2/14 future tasks and three arms give **360 rows**, not 360 independent users. A common cold prefill is shown separately and excluded from incremental costs. At 14 tasks, stock and gate each completed 48 of 60 fixture/position/cache combinations, RAW 24 of 60. We did not count an overflowed run as cheaper for stopping early. Across the 20 gate/stock contrasts *per* cache assumption:

| Cache regime; 14 follow-ups | Cached/fresh price ratio | Gate cheaper / equal / dearer / incomplete |
|---|---:|---:|
| Reusable prior request | 0.10 | 8 / 8 / 0 / 4 |
| Prior request expires before users 1, 5, 9, 13 | 0.10 | 0 / 8 / 8 / 4 |
| No cache, known to gate | 0.10 | 0 / 16 / 0 / 4 |

**The same data can reverse the recommendation.** In the no-revisit partial-release fixture, delaying combined two batches into one, releasing the same 28,133 estimated tokens. With a hot, cheap cache the incremental cost went 121,757 → 103,838 fresh-token equivalents. The gate saved 31,074 fresh tokens but carried 131,549 extra cache-read tokens; the break-even read price was about 0.236 of fresh. At r=0.50 it *lost* (313,136 → 347,836). At r=0.10 with expiry it also lost (202,861 → 265,191). Peak sent context grew 46,034 → 60,094. In the dense case stock's existing hysteresis already performed the same single batch: no improvement over stock. Relative to RAW the same batch was worse over two hot continuations, better over fourteen. In the insufficient-eligible case even the 90% escape could find no admissible batch and the next oversized request was **not sent**. This is a reason for a separate emergency/native-compaction path, not for relaxing original-evidence safeguards. The stock replay was independently rerun to byte-identical output (`e7c773d2…672ed`).
