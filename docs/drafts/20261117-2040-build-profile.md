Analysis only. No product code, tests or Nix expressions were changed. Raw data
(timestamped logs, CPU samples, drv-path JSON, CSV, harness scripts) is in
`/home/pavel/work/flakes/ponygirls/.local/overhaul-20261117/reports/build-profile/`
(referred to below as `$R`). Every number is **measured** (command and log named)

The host was heavily loaded (1-min load 133–181 on 128 CPUs) throughout; see §10.

## 1. Executive summary

Owner hypothesis: "native-image is not the key offender; there are too many tests".

* **For the deployable packages the hypothesis is false.** A backend source change
  rebuilds each service package in 114–131 s (measured end-to-end). The critical path
  is sbt start-up + compile/assembly (~45–55 s) followed by GraalVM native-image
  (69–75 s, 56–59 % of the path). Tests on that path take ≤ 5 s (Chronicle only) and
  run in a parallel derivation that finishes before native-image does (0 s of
  critical path).
* **For `nix flake check` and the agent "full verification" path the hypothesis is
  half-true.** Test execution is > 90 % of the time, but the cost is not driven by the
  number of tests. It comes from (a) a handful of suites with real-time waits:
  4 Chronicle suites with 25 tests take 399 s of the 913 s Chronicle backend run, and
  2 Haystack transport tests take 94 s of 204 s; (b) strictly serial execution at
  0.3–1.0 effective cores on a 128-core host; (c) cache misses: the mandated full
  suites are not Nix derivations, and several checks rebuild on unrelated changes.
* The three largest levers are structural, not test deletion:
  1. parallelize the serial suites (Chronicle backend: 913 s at ~0.65 cores;
     Chronicle browser: 601 s at 0.61 cores; Manure target: 906 s at 0.62 cores);
  2. make the agent-mandated full suites exact-input Nix derivations, so an
     unchanged backend is a cache hit (currently ~26 min of agent wall time for every
     Chronicle task, measured);
  3. remove spurious invalidations: `self.rev`/`self.outPath` in 4 checks and
     over-broad sources that re-run 220–232 s checks on dashboard-only or web-only edits.

Deployment vs check-only:
* A NixOS/Home Manager deployment realises only `pkg chronicle|haystack|manure`
  (modules call `mkChroniclePackage`/`mkHaystackPackage`/`mkManurePackage`). Of
  the test-running derivations, the deployment path contains only: Chronicle fast
  backend gate (5 s of tests), Chronicle protocol (≈0.2 s), Chronicle web
  `npm test` (0.6 s), Haystack web `npm test` (14 s), Manure viewer `npm test`
  (0.3 s).
* Everything else (`haystack-native`, `haystack-browser`, `manure-backend`,
  `manure-native`, VM tests, `backend-*`) is reached only by `nix flake check` or
  an explicit `nix build .#checks…`.
* The Chronicle full backend suite (1,009 tests), the Chronicle browser suite and
  the Haystack JVM `testFull` (715 tests) are **in no Nix derivation**. They are
  paid only through the agent path in AGENTS.md (§8).
* Duplicate test execution: `manureStorage/testFull` runs in both
  `backend-foundation` and `manure-backend` (33 tests, ~4 s plus a separate sbt
  start-up and compile). `manure-browser` is an alias of `manure-native` (no duplicate).

## 6. Parallelism audit

Host/Nix (`nix config show`): 128 CPUs, `max-jobs = 8`, `cores = 16`, sandbox on,
`use-cgroups = false`, no remote builders (`/etc/nix/machines` absent),
system-features `benchmark big-parallel nixos-test uid-range`.

* **Independent derivations do build concurrently.** In G1, native and the fast gate
  started in the same second. Chronicle's test gate (68 s) is therefore hidden behind
  native (126 s). No false chain was found on the package paths. `manure-unittests`
  composes 4 real checks; `chronicle-validation` needs the native output because the
  receipt binds the ELF digest. The gate dependencies are policy, not artefacts of
  the build, but they cost no wall time today.
* **native-image**: `--parallelism=min(NIX_BUILD_CORES,8)`, `-J-Xmx24g`; the reported
  CPU load is 10.5–10.6, i.e. the derivation already uses ~10 cores. Raising the cap
  above 8 is untested (estimated gain ≤ 10–20 s; not measured).
* **sbt compile** in the sandbox reaches 8–10 effective cores (A02 8.0, A11 9.9).
* **sbt tests**: `Test / fork := true` with `Test / parallelExecution := false` for
  every service project, so each project's suites run serially in one forked JVM.
  The Chronicle comment says why: "PostgreSQL suites truncate shared tables and mutate
  profile state". `test-postgres.sh` starts one owned cluster and gives every suite the
  same `postgres` database. Measured effective parallelism of the Chronicle test phase:
  ~0.65 cores locally (H03: 611 CPU-s / 936 s, PG excluded) and 1.04 in the sandbox
  including compile. Haystack's 715 tests finish in 37 s, so serial execution matters
  there only marginally. `manure-backend` sets `-XX:ActiveProcessorCount=4` and runs
  at 1.5 cores.
  * Cheapest safe parallelization: sbt `Test / testGrouping` into N forked JVMs, each
    given its own database (`CREATE DATABASE … TEMPLATE` per group, inside the same
    owned cluster; Manure already uses `MANURE_TEST_ALLOW_CREATEDB`). Suites that
    mutate global profile state stay in one group. Estimated wall with 6 groups and
    longest-processing-time packing: ≈ 150–230 s, bounded below by ModelTransportTest
    141.5 s (estimated, not measured).
* **Chronicle browser suite**: `test:browser` is a 20-command `&&` chain; each script
  starts its own Vite server on `port: 0` and its own Chromium. Measured 601 s serial at
  0.61 cores (D2). Running the scripts in a bounded pool of 4 needs a guard against
  races on the shared Vite cache directory (`chronicle/web/.cache`); estimated wall
  150–160 s, bounded by `rebuild.mjs` at 98 s. Risk: the timing-sensitive UI
  assertions failed 3 times under load (D, below).
* **Node tests**: Chronicle web `npm test` already parallel (14.7 CPU-s in 1.2 s);
  Haystack native transport forces `--test-concurrency=1` (0.3 cores; 94 s are two
  real-time 30 s heartbeat cases). Running test files concurrently with per-file
  provisioned databases (`HAYSTACK_TEST_PROVISION_COMMAND` exists) would bound the wall
  near the 62 s case; estimated saving 100–140 s.
* **Python**: Manure `target-suite.py` runs one `unittest.TextTestRunner` over all 412
  tests (906 s, 0.62 cores). Sharding by module across processes with per-shard
  provisioned databases is the analogue; the saving is unknown without per-module times
  (the run log prints no per-test durations; owned by the Manure triage agent).
* **VM tests**: separate derivations, already parallel with each other under `max-jobs`.
  Their cost is repeated re-execution (§3, `self.rev`), not serialization.
* **`nix flake check`**: evaluating all 112 checks took 102 s single-threaded before any
  build (measured: `nix eval --json .#checks.x86_64-linux --apply …drvPath`). The
  critical path of the check build is estimated at manure.native (≈2 min) → manure-native
  (≈15 min) → manure-unittests, ≈ 17–18 min plus evaluation.

## 7. Non-test overheads

1. **Repeated sbt start-up and compilation.** Every sbt derivation boots the launcher and
   loads 23,337 settings for 18 projects (15–17 s, single-threaded), then compiles the
   shared modules and the 112-source Scala 2.13 contracts again. A Chronicle main edit
   compiles twice (native + fast gate, ≈ 45 s and ≈ 500 CPU-s duplicated). A `shared/`
   or `build.sbt` edit rebuilds 9–10 sbt derivations (chronicle native + gate, haystack
   native, manure native, manure-backend, backend-foundation, coassembly, rites-backend,
   posix-acceptance): ≈ 2.5 min sbt start-up and 5–8 min compile summed. This is mostly
   CPU, not wall, because the derivations run in parallel.
2. **Local versus sandbox compile.** Outside Nix, sbt 2's per-user disk cache
   (`~/.cache/sbt`, 1.6 GB, shared by all worktrees) reached 100 % hits even in a fresh
   detached worktree (H03 compile 3 s against 51 s cold in the sandbox). Agents already
   pay almost no compile cost locally; this cache cannot be reused inside the sandbox.
3. **Over-broad sources that cause spurious reruns (verified in §3):**
   `manureTargetTests` includes the whole `manure/` tree, so the JVM `manure-backend`
   (221 s) re-runs on dashboard, viewer, Python-test and docs edits.
   `haystack/test-dependencies.nix` reuses `web.src`, so the node_modules derivation,
   and with it `haystack-native` (232 s), rebuilds on every Haystack web edit.
   `self.rev` in haystack-browser and both unit-graph VM tests re-runs them on every
   commit. `backend-runner-contract` copies the whole repository via `self.outPath` and
   rebuilds on every edit; it is cheap (≈0 s), but `nix flake check` must still copy
   the repository.
4. **Dependency reconstruction is cheap**: coursier-cache assembly 1–3 s (761 FOD jars
   reused); `npmConfigHook` 1.7–4.3 s per npm derivation; launcher bootstrap ~2 s per sbt
   drv.
5. **Receipts/evidence**: validation-inputs + receipt + wrapper verify = 1.8 s (A10);
   haystack/manure receipts are sub-second steps inside their checks. Negligible.
6. **chronicle-offlineAssembly** (58 s) is passthru only; no check or package builds it.
7. **Evaluation**: 102 s for the whole check set, ≈ 70 s for 54 selected attributes,
   ≈ 3 s for one package (`nix build .#chronicle`).

## 9. Ranked proposals

The savings are derived from the measurements above. Savings marked *est.* are
projections, not measurements.

### Cache better / fix invalidation (do first: low risk, no test semantics changed)

1. **Turn the agent-mandated full suites into exact-input Nix derivations**
   (Chronicle full backend, Chronicle browser, Haystack JVM `testFull`). Prior art: the
   historical `chronicle-full-backend-validation` derivation; the ad-hoc harness
   `$R/tools/adhoc-sbt.nix` already runs the Chronicle and Haystack suites green in the
   sandbox. AGENTS.md already allows "exact-input cached evidence … when its
   source/artifact binding is verified". Saving: the full ≈ 936 s + 601 s on every task
   that does not change those inputs. For example, HEAD f153d1ae touched only `chronicle/collector/**` (12 files,
   `git diff --stat`); for that commit ≈ 25 of the 26 min would have been a cache hit. Risk: low, provided source boundaries are tight
   (see 3). Effort: medium (browser leg needs Chromium in the sandbox, as `haystack-browser`
   and `manure-native` already have).
2. **Remove `self.rev` / `self.outPath` from check inputs** (haystack-browser,
   service-unit-graph-vm, hm-service-unit-graph-vm, backend-runner-contract). If the
   revision is needed, record it outside the derivation (e.g. post-build receipt
   annotation). Saving per commit in `nix flake check`: ≈ 170 s + 350 s + 310 s builder
   time (hist. medians). Wall saving is smaller while manure-native dominates the critical
   path. Risk: low. Effort: low.
3. **Tighten source sets**: give `manure-backend` a JVM-only source (not
   `manureTargetTests`), and key Haystack test `node_modules` on
   `package.json`/`package-lock.json` only. Saving: 221 s per Manure web/Python-test/doc
   edit; 232 s per Haystack web edit (verified by probes c2/c3/c4/b4). Risk: low; it
   needs an identity test like `backend-source`. Effort: low.
4. Drop the duplicate `manureStorage/testFull` from `backend-foundation` or from
   `manure-backend`. Saving ≈ 30 s of sbt start-up+compile CPU; wall ≈ 0. Low priority.

### Parallelize test execution (largest wall savings; medium risk)

5. **Chronicle backend: `testGrouping` into ~4–6 forked JVMs with a database per group.**
   912 s at ~0.65 cores → est. 150–230 s (floor 141.5 s). Saving est. 680–760 s per
   agent run. Risk: shared-table truncation and profile state must be isolated per
   group; real deadline tests may become flaky under CPU contention (load is already
   ~150). Effort: medium. Combine with triage of the 4 suites that take 44 %.
6. **Chronicle browser scripts in a bounded pool (4).** 601 s → est. 150–160 s (floor
   98 s). Saving est. ≈ 440 s. Risk: shared Vite cache; timing-sensitive UI assertions
   (3 failures were observed under exhaustion/load). Effort: low–medium.
7. **Manure target suite sharding** (906 s at 0.62 cores). Saving unknown without
   per-module times; probably several minutes. Risk: medium (browser + owned PG per
   shard). Effort: medium.
8. **Haystack transport: drop `--test-concurrency=1`, per-file databases.**
   204 s → est. ~70 s. Saving est. 100–140 s. Risk: low–medium. Effort: low.
9. **manure-backend JVM grouping**: 135 s at 1.5 cores → est. 60 s. Saving est. ~75 s.

### Restructure the build graph (small or CPU-only gains)

10. One shared "JVM build" derivation (sbt compile + all assemblies + test classes), with
    native-image and test derivations consuming its outputs. It saves 2–9 redundant sbt
    start-ups and compiles: ≈ 0.5–3 k CPU-s per JVM change. Wall impact ≈ 0 for a
    single package (the compiles already run in parallel), and it can lengthen the
    critical path. Recommend only if CPU contention on the shared host is the concern.
11. The Chronicle deployment wrapper rebuilds on test-only edits (67 s, G2) by policy.
    Moving the fast gate from a build input to a check would make test edits free for
    deployment. This is a policy change (see Open questions), not a speed-up of the
    first build.
12. native-image: no structural change is recommended. It is ~70–75 s per service at
    ~10.5 effective cores, built once per backend edit, and runs in parallel with the
    gate. `-Ob` (quick build) would shorten dev-only artefacts but must not be used for
    deployment (not measured).

**Does the owner's hypothesis hold?** Partly. "native-image is not the key offender"
holds for checks and agent runs, but not for package builds: there native-image is the
largest single phase (56–59 %). Tests are absent from the Haystack/Manure backend-edit
path and off the critical path for Chronicle (5 s in a parallel derivation); the largest
in-package test step is Haystack web `npm test` at 14 s, which runs only on web edits. "Too many tests" is the wrong diagnosis for the check and agent cost.
The cost sits in a few real-time suites executed serially at ≤ 1 core, and in cache
misses (full suites outside Nix; spurious invalidations). Deleting low-value tests
cannot recover most of it: the 1,009-test Chronicle suite would still take ≈ 400 s from
its 4 slowest suites alone. Parallelism plus exact-input caching can.

## 10. Measurement conditions and limitations

* Source: commit f153d1ae (worktree clean except during reverted probe edits).
  Date 2026-11-17, 20:37–21:30Z.
* Load: 1-min load average 133–181 on 128 CPUs during all runs, caused by ≈ 8 other
  agents (each run's start/end load is in `$R/run-timings.csv` and the log headers). My
  own queues overlapped one another: package rebuilds ran concurrently with the
  Chronicle full-backend runs and the browser scripts. Repeats: Chronicle full backend 3×
  (983 / 945 / 936 s, ±2.5 %); browser suite 2× (625 / 601 s); per-suite top times
  reproduced within ±8 %. Native times are 10–30 % above historical medians.
* CPU sampling is a lower bound (1 Hz; misses short processes). CPU via `time` excludes
  daemonized PostgreSQL. A sampler uid can include other agents' builds when uids are
  reused; uids were matched by time window and command-line tokens (`$R/tools/cpu-summary.py`).
* `--rebuild` measures a derivation with warm inputs. The e2e G-runs measure eval +
  build after a real probe edit. VM tests were not run (no KVM in this sandbox); their
  numbers are historical log durations.
* The rebuild matrix covers 54 named nodes, not all 112 checks (non-service checks
  were excluded). (f) `flake.lock` is inferred.
* **inotify hazard.** Nix sandbox builds are confirmed unaffected: sbt-based builds A01,
  A02 and C-chronicleFull ran successfully at 20:45–20:51Z while user pavel's limit was
  exhausted, as build users (uids 30001–30003 observed). Local sbt (B03/B04) failed at
  project load in that window. Timings under the LD_PRELOAD shim: **only E03, E04,
  E05**. The clean equivalents H03/H04/H05 were rerun without the shim after the limit
  was raised; H03 matches E03 within 1 %. B05–B10 and the browser run D ran unshimmed
  while the limit was exhausted. D showed Vite `EMFILE` watcher errors and 3 script
  failures, which did not recur in the clean rerun D2. This is a correlation; the cause
  was not established.
* Failures observed and not investigated (handed to the triage agents): manure-native
  `DashboardUXTests.test_catalogue_detail_and_session_flows` (A16, under load);
  Chronicle browser `ux`, `goal50`, `popup-regression` (exhausted run only).
* Ad-hoc harnesses (`$R/tools/adhoc-sbt.nix`, queue scripts) are analysis tooling only
  and are not part of the repository.

## Open questions (with recommendation)

1. May the Chronicle full backend and browser suites become Nix derivations whose
   cached result satisfies AGENTS.md's final-run requirement for unchanged inputs?
   *Recommend yes* (proposal 1); AGENTS.md already permits exact-input reuse.
2. Should the deployment wrapper keep depending on the fast backend gate (rebuild on
   test-only edits)? *Recommend keeping it for now*: it costs 0 s of wall on backend
   edits and 67 s on test-only edits.
3. Is per-group database isolation acceptable for Chronicle suites that "truncate shared
   tables and mutate profile state"? *Recommend* asking the Chronicle-backend triage agent
   to classify suites into isolatable groups before implementing proposal 5.
